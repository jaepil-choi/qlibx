# 한도(constraint)와 감시 clock — closed loop mental model 재검토

- 상태: 조사·설계 기록 (thoughts). 결정된 설계가 아니다.
- 대상 브랜치/커밋: `exp/one-shot` @ `7776c6a`
- 계기: "built-in optimizer를 제공하되 사용자가 custom할 수 있어야 한다"에서 출발한 논의가,
  optimizer의 성격과 감시(monitoring)의 clock 문제로 번졌다.
- 자매 문서: [`decision-clock-and-rebalance-trigger.md`](decision-clock-and-rebalance-trigger.md).
  그 문서가 intraday 시나리오에서 발견한 것과 **같은 구조적 결함을, 훨씬 평범한 경로로** 다시
  만난다.

## 1. 한 줄 결론

**qlibx는 지금 "행동한 시점의 포트폴리오"만 기술할 수 있고, "아무것도 하지 않은 시점의
포트폴리오"를 기술할 수 없다.** 그런데 컴플라이언스 감시는 후자를 요구한다. 이것은 intraday
전략 같은 특수 요구가 아니라 **월 1회 리밸런싱 + 일별 한도 점검**이라는 가장 평범한 기관 설정에서
바로 막힌다.

## 2. 논의에서 확정된 것

### 2.1 여기서 말하는 optimizer는 목적함수 optimizer가 아니다

두 개의 서로 다른 물건이 "optimizer"라는 한 단어를 쓰고 있었다.

| | 배치 optimizer (기존) | constraint optimizer (요구) |
| --- | --- | --- |
| 위치 | `portfolio.construct_enhanced_index` → `optimization.py` | 전략 출력과 Qlib 실행 사이 |
| 성격 | 추적오차 최소화. 목적함수를 가진 수학적 최적화 | 규정에 맞게 주문을 다듬는 컴플라이언스 단계 |
| 시점 | 배치, 1회 | 매 결정 시점 |
| 실패 시 | `status="soft_relaxed"` 등으로 **반환** | 아래 2.2 |

"사용자 optimizer를 끼울 수 있나"라는 질문에 대한 초기 조사가 전자를 대상으로 이루어졌고, 그래서
"목적함수를 못 바꾼다"는 결론이 나왔다. 요구는 후자였다.

### 2.2 다듬기는 게이트가 아니다

못 지켜도 **그대로 실행된다.** 10주 한도인데 9주 보유 상태에서 2주 주문이 나가고, 다듬은 뒤에도
그대로면 그 주문은 나간다. 그리고 같은 한도로 감시하는 모듈이 위반을 보고한다.

컴플라이언스를 주문 게이트에서 강제하면 안 되는 이유가 셋이다.

1. 막는 것이 더 나쁠 수 있다. 한도를 넘었다고 주문을 막으면 빠져나올 수 없는 상태에 갇힌다.
2. 막아도 못 막는다. 위반의 상당수는 주문이 아니라 가격 변동·부분 체결·기업행위에서 수동적으로
   생긴다. 주문 게이트가 닿지 않는다.
3. 막으면 거짓이 된다. "위반이 불가능한 시스템"은 백테스트를 현실과 다르게 만든다. 요구는 위반이
   **없는 것**이 아니라 **알려지는 것**이다.

이는 이미 이 저장소의 방식이기도 하다. `construct_enhanced_index`는 제약을 못 지킬 때 예외를 던지지
않고 `status`·`binding_constraints`·`constraint_residual`을 결과로 반환한다
(`portfolio.py::_infeasible`). "못 지킨 것은 예외가 아니라 결과다"라는 원칙이 이미 있고, 이 논의는
그것을 closed loop로 확장하는 것이다.

다만 실행 **가능성** 검사는 남는다. `NaN`, long-only인데 음수, 레버리지 없는데 합이 1 초과는 Qlib이
실행 자체를 못 하는 것이므로 계약 위반이고 계속 실패해야 한다. 지금 `execution.py:286` 부근의 검사가
이 둘(계약 위반 / 한도 위반)을 구분하지 않고 한데 두고 있다.

### 2.3 한도의 추상화

**한도 = 이름 + 점검값(들) + 각 점검값의 [min, max].** 위반은 이진 판정이다.

필수 키는 넷(한도명, 점검값명, min, max)이고 나머지는 사용자 자유다. qlibx는 나머지를 해석하지 않고
**위반 보고서에 원문 그대로 실어 나른다.** 준법 담당자가 한도코드로 역추적할 수 있어야 하기
때문이다.

```yaml
limits:
  - name: 각 상장지수집합투자기구 동일집합투자증권 총수 50%제한
    metrics:
      - metric: etf_ownership_ratio
        min: null
        max: 0.5
    # ↓ qlibx가 읽지 않고 보존만 하는 영역
    법규: 자본시장법
    한도코드: Z31212
    시작일: 2009-02-04
    종료일: 2999-12-31
    OMS코드: T01R07
    detail: |
      [같은 집합투자기구 ETF 보유수량 / 같은 집합투자기구 발행 ETF 총수] ≤ 50%
      ☞ 예외 : 운용사지정펀드(6970화면 4번에 등록한 펀드는 100%까지 가능)
```

한도 하나가 점검값 여러 개를 가질 수 있다. **여러 점검값을 어떻게 종합해 "한도 위반"으로 판정할지는
qlibx가 정하지 않는다** — AND인지 OR인지는 사용자 구현이다. qlibx는 각 점검값의 측정치와 범위 이탈
여부라는 **사실만** 보고한다.

측정 결과는 스칼라가 아니라 이름표 붙은 값들이어야 한다. ETF 규칙은 종목별, 섹터 한도는 섹터별,
회전율은 스칼라다. 위반 보고에 "어느 종목이" 가 들어가야 한다.

기존 원칙과의 정합: 데이터 등록에서 "opaque information column"을 의미 부여 없이 기록만 하는 것과
같은 태도다. 다만 프로젝트 설정 로딩은 지금 **모르는 키를 거부**한다
(`_vendor/qlib_engine/enhanced_config.py:29-31`). 한도 선언은 반대 규칙이 필요하다 — 아는 키만
검증하고 나머지는 원문 보존. 의도적 예외이므로 그 이유가 기록되어야 한다.

### 2.4 검증은 지연된다

한도 선언이 잘못되어 있어도, 그것에 의존하는 계산이 돌지 않으면 오류가 나지 않는다. 쓰지 않는 한도
때문에 run이 막히면 안 된다. 즉 로딩은 관대하게, 검증은 사용 시점에.

### 2.5 점검값의 데이터는 전략 구독 데이터의 부분집합이다

점검값이 자기 데이터 요구를 따로 선언하지 않는다. 필요한 데이터가 있으면 **전략이 구독해준다.**

이 결정의 값어치는 단순함이 아니라 안전이다. 구독 표면이 하나로 유지되므로 **점검값이 전략보다 넓게
보는 사고가 구조적으로 불가능해진다.** capability requirement 프로토콜(PRD §5.4/§5.5)을 점검값에
붙이려던 초안은 이 결정으로 폐기했다.

## 3. 진짜 분리선 — 정보 경계

| | 내부 constraint optimizer | 감시(monitoring) |
| --- | --- | --- |
| 볼 수 있는 데이터 | 전략 구독분만, **구독한 길이만** | 같은 구독분 |
| 더 필요하면 | 스스로 strategy memory에 남기는 수밖에 없음 | — |
| 언제 도나 | **전략이 trigger될 때만.** 안 돌면 계산할 필요도, 방법도 없음 | 데이터 해상도마다 또는 지정 주기 |
| 전략 상태 | 자기가 그 안에 있음 | **전략이 안 돌아도 읽는다** |
| 보는 상태 | 보유 + 나갈 주문, **체결을 가정한 가상 상태** | **실제 계좌** |
| 정확성 | 근사 (5.2 참조) | 정확 |

optimizer가 전략보다 넓게 보면 그것은 look-ahead다. 감시가 t 시점 계좌를 t 시점에 확인하는 것은
경계 위반이 아니다 — 다른 시점의 사실을 볼 뿐이다.

그리고 **"전략이 안 돌면 다듬을 수도 없다"**가 핵심이다. 월 1회 리밸런싱 전략의 optimizer는 월 1회만
개입할 수 있고, 그 사이 매일 생기는 위반은 구조적으로 막을 수 없다. 이것이 2.2의 "못 지켜도 나간다"와
앞뒤가 맞는 지점이자, 감시가 별도로 존재해야 하는 이유다.

## 4. 지금 코드가 이미 만족하는 것

의외로 많다. 이 논의가 요구하는 이음매의 상당수가 이미 존재한다.

**전략이 알아야 할 상태는 이미 있다.** `strategy.py:113-123`의 `DecisionContext`가 `decision_time`,
`account`(보유 수량·비중·현금·NAV), `memory`, `feedback_history`, 그리고 **구독 데이터를 그 시점까지·
구독 길이만큼 잘라준 프레임**을 들고 있다.

**전략 출력과 Qlib 사이에 qlibx가 소유한 지점이 있다.** `execution.py:226`의 `target_policy` closure가
그것이다. Qlib이 매 결정 시점에 이것을 호출하고, closure는 계좌 상태를 받아 데이터를 자르고 전략을
호출한 뒤 결과 weight를 돌려준다. 다듬기를 놓을 자리가 이미 있고, 필요한 상태를 전부 쥐고 있다.
현재 그 자리에 있는 것은 다듬는 물건이 아니라 **거부하는 검사기**이고, 그 에러 메시지가 문자 그대로
"전략이 알아서 clip하거나 renormalize해서 오라"고 말한다. 즉 **지금 이미 "전략 안에서 해결" 상태이되,
도구는 주지 않고 책임만 넘긴 형태다.**

**전략 상태가 시점별로 이미 기록된다.** `DecisionResult`(`strategy.py:302-310`)가 `memory`,
`diagnostics`, `intermediates`를 갖고, `StrategyExecutionResult.decisions`가 **매 결정 시점마다 전부**
돌려준다. 계좌·포지션은 표로 남는다. 따라서 "t 시점의 계좌 + t 이전 마지막 결정의 memory"를 저장된
표만으로 재구성할 수 있다 — **전략을 다시 돌리지 않고 감시가 가능하고, 지난 run을 새 한도로 재검사할
수도 있다.**

**사용자 코드를 받는 통로가 있다.** extension contract가 셋(`signal_transform`, `exposure_analyzer`,
`report_renderer`) 있고, 소스 digest 기록·계약 검증·extension root 제한이 이미 규칙으로 서 있다.
점검값은 넷째로 들어가면 된다.

## 5. 그래서 새로 필요한 것

1. **한도 선언** — YAML 형식(필수 4키 + 원문 보존), 타입, 지연 검증. 다듬기·감시·배치가 공유한다.
2. **`DecisionContext`에 한도를 싣기** — 시작일/종료일을 qlibx가 해석하지 않기로 했으므로 전략이 직접
   읽고 판단해야 한다. 지금 전달 통로가 없다.
3. **점검값 확장점** — 입력 (포트폴리오 상태 + 이미 잘린 구독 데이터), 출력 이름표 붙은 값들.
4. **감시** — 순수 함수 `(상태 스냅샷, 한도) → 사실`. 루프 안에서도, 저장된 표 위에서도 호출 가능.
5. **다듬기** — 확장점 + built-in 하나. 결과에 못 지킨 초과분 기록.

### 5.1 제약 선언 타입의 위치 — kernel 문제는 이 설계에서 사라진다

별도 조사에서 "`optimization`을 kernel 밖으로 옮겨야 하는가"가 쟁점이었다. `optimization`은 layer 0이라
`errors`를 import할 수 없고, 따라서 `LinearConstraint` 생성자 검증이 stage 없는 `ValueError`로 나온다.
옮기면 `_vendor/qlib_engine/enhanced.py:9`의 import가 vendor 규칙을 위반한다.

이 설계에서는 **모듈을 옮길 필요가 없다.** 옮길 것은 모듈이 아니라 **사용자가 만지는 선언**이다.
한도 선언을 `errors`만 쓰는 layer 1에 두고, kernel의 optimizer는 숫자만 받는 계산 엔진으로 남긴다.
경계에서 번역한다. 확장점 계약 검증은 `extensions.py`(layer 5), 다듬기는 `execution.py`(layer 4)에
있고 둘 다 이미 `errors`를 쓴다.

### 5.2 정직하게 남길 비대칭

**감시는 정확하고 다듬기는 근사다.**

점검값이 임의의 사용자 함수(블랙박스)이면 감시는 "계산하고 범위와 비교"라 정확하다. 다듬기는
역방향 문제다 — "이 함수의 출력이 범위에 들어오게 하는 주문"을 찾아야 하는데 함수 내부를 모른다.
할 수 있는 것은 측정 → 이탈 이름표 확인 → 그쪽을 한도 방향으로 밀기 → 재측정을 정해진 횟수만큼
반복하는 것뿐이고, 수렴 보장이 없다.

이 한계가 2.2의 "못 지키면 그대로 나간다"와 정확히 맞물린다. 설계가 일관된다. 그리고 이것이 다듬기도
사용자 확장점이어야 하는 이유다 — 자기 한도가 선형이라는 것을 아는 펀드는 제대로 푸는 다듬기를 직접
쓸 수 있어야 한다.

## 6. 여기서 mental model이 깨진다

이제 자매 문서의 발견과 만난다.

### 6.1 지금 모델: 하나의 달력, 모든 행이 관측=결정=실행

자매 문서 §2가 확인한 사실이다. decision clock은 **`execution_price` matrix의 `DatetimeIndex`** 단
하나에서 나오고, 그 index의 모든 행이 decision time이자 execution time이자 rebalance다.
`_normalize_targets`가 target index와 execution_price index의 **정확한 일치**를 요구하는 것이 두 clock을
묶어버리는 지점이다.

### 6.2 감시는 네 번째 clock을 요구한다

논의가 확정한 clock은 최소 넷이다.

| clock | 무엇이 일어나나 | 지금 |
| --- | --- | --- |
| 관측 | 데이터가 도착한다 | 실행 달력과 동일 |
| 결정 | 전략이 의도를 만든다 | 실행 달력과 동일 |
| 실행 | 주문이 체결된다 | 실행 달력 |
| **감시** | 상태가 한도를 어겼는지 확인한다 | **존재하지 않음** |

그리고 감시 clock은 결정 clock과 **독립이어야 한다**는 것이 요구사항의 명시적 부분이다. "전략이 돌지
않아도 전략의 state를 읽을 수 있어야 한다."

### 6.3 결정타 — 가장 평범한 설정이 표현 불가능하다

**월 1회 리밸런싱 + 일별 한도 점검.**

- 일별로 감시하려면 계좌 상태가 일별로 존재해야 한다.
- 계좌 상태는 루프가 도는 달력의 행마다 생긴다.
- 그 달력이 곧 결정 달력이다.
- 따라서 일별 감시를 원하면 전략이 **매일 호출되고 매일 리밸런싱**한다.
- 월 1회 리밸런싱을 원해 달력을 월별로 만들면, **그 사이 29일간 계좌 상태가 존재하지 않는다.**

자매 문서는 이 결함을 minute bar 시나리오(§4.2 "구조적으로 불가")에서 발견했다. intraday를 out of
scope로 선언하면 피할 수 있는 문제로 보였다. **컴플라이언스 감시는 그 도피로를 막는다.** 일봉
데이터에 월간 리밸런싱은 특수 요구가 아니라 기본값에 가깝고, 일별 한도 점검은 선택이 아니다.

### 6.4 근본 명제

> **qlibx는 행동한 시점의 포트폴리오만 기술할 수 있다. 컴플라이언스는 아무것도 하지 않은 시점의
> 포트폴리오를 기술할 것을 요구한다.**

"all-data-frequency closed loop"라는 모델에는 **정지 상태(state at rest)**의 자리가 없다. 상태는
연속이고 사건은 점인데, 지금 구조는 사건이 있는 곳에서만 상태를 만든다.

## 7. 선택지 재평가

자매 문서 §6이 A(dense calendar + hold 반환)와 B(trigger를 1급 개념으로)를 열어두고 "진짜 intrabar
event가 필요한지"를 갈림 기준으로 삼았다. 감시 요구가 이 저울을 A 쪽으로 크게 기울인다.

**A가 감시 요구를 직접 충족한다.** 일별 달력 + 전략이 비리밸런싱일에 hold 반환 → 계좌 표에 일별 행이
생김 → 일별 감시가 저장된 표만으로 성립. 게다가 hold 계약은 감시에 필수적이다. hold가 없으면 전략은
매 bar 전체 weight vector를 반환해야 하고, 가격 drift만큼 미세 리밸런싱이 발생하며 lot rounding 때문에
실제 주문까지 나간다(자매 문서 §4.3). 그러면 감시가 보는 위반이 **실제 위반인지 모델 잡음인지 구분되지
않는다.**

**A에서 다듬기와 hold의 결합 규칙이 자연스럽게 나온다.** 결정이 주문을 만들지 않으면(hold) 다듬을
것이 없다. 즉 **다듬기는 주문이 생기는 결정에서만 돈다.** 이것이 3절의 "전략이 trigger될 때만"을 구현
수준에서 실현한다.

**B는 staleness 개념을 추가로 요구한다.** 결정 달력이 성기면 전략 상태는 결정 시점에만 존재하고, 그
사이 감시는 "마지막 결정 시점 기준 상태"를 읽는다. 의미상 옳지만, 기록에 "as of"를 명시해야 하고
보고서가 두 시각을 들고 다녀야 한다. A에는 그 부담이 없다.

**A의 비용은 감시가 키운다.** dense calendar는 매 bar 전략 호출을 뜻하고, 자매 문서 §4.4가 지적한
loader 성능 문제가 전제 조건이 된다. 여기에 점검값 평가가 얹힌다. 완화책은 명확하다 — **감시를
in-loop 콜백이 아니라 저장된 상태에 대한 pass로 구현한다.** 루프 비용이 늘지 않고, 지난 run 재검사가
공짜로 따라온다. 순수 함수 형태가 이것을 가능하게 하는 조건이다. 라이브에서의 "실시간" 감시는 같은
함수를 다른 호출 지점에서 쓰는 배포 문제이지 설계 문제가 아니다.

## 8. 두 실행 경로 문제가 여기서도 재현된다

자매 문서 §3이 manifest 경로(plain pandas)와 adaptive 경로(`DecisionContext`)의 능력 차이를 기록했다.
manifest 경로에는 memory와 feedback이 **없다.**

이 논의는 그 격차를 넓힌다.

- 다듬기가 "더 필요하면 스스로 strategy memory에 남긴다"에 의존한다 → **manifest 경로에서는 성립하지
  않는다.**
- 다듬기가 계좌 상태(현재 보유)를 봐야 한다 → manifest 경로의 전략은 계좌를 보지 못한다.
- 따라서 **내부 constraint optimizer는 adaptive 경로에서만 가능하다.**

PRD가 모든 StrategyAgent에 memory/feedback을 약속하는데(§7.2) manifest 경로가 제공하지 않는다는 기존
갭이, 이제 "컴플라이언스 다듬기를 쓸 수 있는 전략과 없는 전략이 갈린다"로 커진다.

## 9. 아직 결정하지 않은 것

1. **다듬기가 전략 코드 안인가, 전략 직후의 선언된 단계인가.** "오직 허용된 주문만"이라는 보장이
   요구에서 빠졌으므로(2.2), 강제 단계여야 할 논거는 약해졌다. 남은 판단 근거는 재사용성과 기록의
   균일성, 그리고 **부모/자식 전략 중첩**이다. 다듬기가 전략 안에 있으면 자식이 다듬고 부모가 또
   다듬는다. 자식의 다듬기는 자기 몫만 보고 하므로 부모 전체 한도와 무관하다. "최종 출력을 내는
   전략만 다듬는다" 같은 규칙이 필요하다.
2. **감시의 기본 주기.** 데이터 해상도 고정인가, 사용자 지정 주기를 받는가.
3. **한도 선언 오류를 어느 stage로 보고할지.** 지연 검증이므로 "사용하는 계산이 도는 시점의 stage"가
   자연스럽다 — 다듬기라면 `EXECUTION`, 전략 안이라면 `STRATEGY_RUN`. 새 stage를 만들면 PRD §5.6
   목록이 바뀌므로 가볍게 결정할 일이 아니다.
4. **hold 계약의 정확한 형태.** 자매 문서 §5-3의 미결 항목이자 이 문서의 전제 조건.
5. **A로 갈 때 loader 캐싱 요구.** dense calendar의 전제.

## 10. PRD에 추가로 빠져 있는 것

자매 문서 §5의 6개 항목에 더해:

7. **감시 clock과 정지 상태.** 상태를 "사건이 없는 시점"에도 기술할 수 있어야 한다는 요구가 PRD에
   없다. §6.4가 이 문서의 핵심 주장이다.
8. **한도(constraint) 선언과 두 소비자.** PRD §2.3이 "조직별 constraint 정의는 사용자 project 소유"라고
   명시하지만, 그것을 선언할 형식도 소비 경로도 정의되어 있지 않다. 현재 백테스트 설정은 `constraints`
   키를 unknown으로 **거부**한다.
9. **다듬기의 정보 경계.** 다듬기가 전략의 정보 경계 안에 있다는 것(구독분만, 구독 길이만, 전략 trigger
   시에만)은 look-ahead 금지의 연장이므로 PRD에 명시되어야 한다.
10. **위반의 지위.** 한도 위반이 실패(예외)가 아니라 관측 가능한 결과라는 것. §2.2.
11. **점검값이 사용자 코드라는 것과 그 계약.** 네 번째 extension contract.

## 11. 다음 행동

이 문서는 결정이 아니라 정리다. 구현 순서를 정하기 전에 **§9의 1번과 §6.4의 수용 여부**가 먼저다.
특히 §6.4를 받아들인다면 자매 문서의 A/B 선택이 이 논의의 선행 작업이 되고, 한도·감시 구현은 그
위에 얹힌다.

받아들이지 않는다면 대안은 하나뿐이다 — **감시 해상도를 결정 해상도와 같게 고정하고, "리밸런싱하지
않는 날의 한도 위반은 관측하지 않는다"를 제품의 명시적 한계로 선언하는 것.** 그것이 정직한
대안이지만, 실제 펀드 운용에서 받아들여질 한계인지는 의문이다.
