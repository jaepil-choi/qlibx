## 0. 왜 이 문서가 있는가

0.9.0의 `src/vqapr`는 층이 DAG이고 순환이 없다(레이어링 캠페인, records `190`-`198`). 그런데
**경계가 선명한 것과 경계가 옳은 것은 다르다.** 소유자가 짚은 네 가지가 전부 같은 곳을 찔렀다.

- `flow`와 `portfolio`가 무엇이 다른가
- `record`·`report`·`analysis`가 무엇이 다른가
- `datamodel`·`strategymodel`은 `authoring`에 있는데 `constraints`·`exchange`는 왜 밖인가
- `account`를 더 추상화할 수 없나

진단해 보면 네 질문의 답이 하나다. **트리가 두 개의 다른 기준으로 동시에 갈려 있다** — 누가 쓰는가
(`authoring`·`extension`·`cli`)와 무엇에 관한 것인가(`data`·`account`·`exchange`·`portfolio`). 두 축이
만나는 자리에서 정확히 위의 네 질문이 나온다.

그 위에 더 큰 것이 하나 드러났다. **매 분 판단하고 매 분 체결하는 전략이 표현되지 않는다.**
`FillConvention`이 "하루 중 한 시각"만 말할 수 있고, 평가가 자기 시계 없이 pending 슬롯에 얹혀 타기
때문이다. 이것은 어휘의 결손이지 모델의 결손이 아니었지만, 그것을 확인하는 과정에서 **시계가 몇
개여야 하는가**가 정리됐다.

이 문서는 그 결과다. **behavior 계약이지 구현 계획이 아니다.**

## 1. 핵심 목표 — provenance

한 문장으로 적으면 이렇다.

> **모든 숫자에 대해 "이것이 어디서 왔는가"에 답할 수 있는 시뮬레이터.**

PRD의 규칙들은 전부 이 한 문장을 지키는 장치다.

| PRD | 지키는 것 |
|---|---|
| §2.2 하나의 execution spine | 수익의 출처가 하나 |
| §2.4 committed state만 authority | 상태의 출처가 하나 |
| §2.3 값과 배분은 다른 역할 | 의미의 출처를 섞지 않는다 |
| §3.2 PIT | 정보의 출처가 시간상 정당하다 |
| §2.5 durable typed artifact | 산출물의 출처가 검사 가능하다 |
| §10.2 explicit failure | 없는 것을 추측으로 메우지 않는다 |
| §9.4 intended와 realized | 의도와 사실을 구분해서 남긴다 |

그 위에 제품 약속이 둘 얹힌다. **누적**(연구 자산이 재사용 가능한 형태로 쌓인다)과
**척추**(수익을 주장하는 순간 반드시 한 경로를 지난다). 둘은 서로 다른 두 개의 루프이며, 만나는
지점은 정확히 하나 — 등록된 데이터셋이다.

## 2. 프로젝트는 그래프다 — run은 화살표다

```text
prices ──[ momentum run ]──► momentum_20d ──[ alpha run ]──► my_alpha ──┐
                                                                        ├──[ ensemble run ]──► ensemble
your_alpha ─────────────────────────────────────────────────────────────┘
```

- **노드는 dataset 하나뿐이다.** 통장(계좌 이력)은 노드가 아니라 화살표에 매달린다.
- **화살표는 run 하나이고, run은 전략 하나다**(§2.3).
- `reads`는 이미 선언된다. **`writes`를 필수로 선언한다** — 이름만.

### 2.1 `writes`가 필수인 이유

```text
대칭    reads 가 필수인데 writes 가 선택이면 비대칭이다
정의    아무것도 안 만드는 run 은 그래프의 규칙이 아니다
규율    "무엇을 만들려는가" 를 만들기 전에 말하게 한다
```

그리고 이름을 **돌리기 전에** 짓게 되므로, "돌리고 나서 이름을 붙이려면 다시 돌려야 한다"는 문제가
발생할 수 없다.

**규칙 한 줄: 선언한 것만 창고에 들어간다. 통장은 항상 생긴다.**

### 2.2 `writes`는 이름만 적는다

스키마는 이미 반대편에 선언돼 있다. 소비자가 `DataRequirement`로 *"이 필드가 이 grain으로 필요하다"*를
말한다. 생산자가 또 적으면 같은 것을 두 곳에 적는 것이고, 두 곳은 어긋난다.

대가는 정직하게 적는다. 그래프만 보고 *"이 사슬이 맞물릴까"*는 알 수 없다. 대신 **창고가 차면서
그래프가 점점 더 검사 가능해진다** — 한 번 만들어진 dataset은 스키마가 등록돼 있으므로 그 다음부터는
사슬 전체를 미리 검사할 수 있다.

### 2.3 run은 전략 하나다

record `139`는 run 하나가 여러 전략을 담게 만들었다. 얼린 층을 공유해야 비교가 된다는 근거였다.
**그 근거는 결정성이 이미 보장한다** — 같은 `reads`·`agenda`·시장 시계를 선언한 두 run은 같은 얼림을
만든다(PRD §1.2-6). 층 공유는 최적화이지 의미가 아니다.

그리고 그래프가 있으면 **병렬화가 더 좋아진다.** 지금 `jobs>1`은 한 run 안의 전략들을 병렬로 돌지만,
화살표가 독립이면 **의존성 없는 화살표가 전부 병렬**이 된다.

비교도 나아진다. 리포트가 "같은 run 안의 전략들"이 아니라 **창고에 있는 것들**을 비교하게 되므로,
지난달에 돌린 전략과 오늘 돌린 전략을 비교할 수 있다.

잃는 것은 *"이 셋을 같은 조건에서 돌렸다"*가 선언에서 안 보인다는 것이다. 대신 화살표마다 얼린 층의
identity가 기록되므로 **사후에 실제로 같았는지 확인**할 수 있다. 주장 대신 증거다.

## 3. 시계는 둘이다

```text
시장 시계   execution table 이 가진 모든 timestamp.  데이터에서 온다.  이미 얼려 있다
전략 시계   agenda 선언.  every · from · to · at.  preflight 가 전개해서 얼린다
```

```text
                     ─────────────────────────────────────────────────►  시간
시장 시계    │      │      │      │      │      │      │      │      │
             ▼      ▼      ▼      ▼      ▼      ▼      ▼      ▼      ▼
        ACCRUE · EXECUTE · VALUATION · COMPLIANCE   (매 점마다)

전략 시계         ▲                            ▲                     ▲
                DECIDE                       DECIDE               DECIDE
```

### 3.1 한 시각의 순서

```text
1. ACCRUE      직전 보유에 대해 발생한 것        → 통장   (자리만, §7.3)
2. EXECUTE     이 시각을 target 으로 하는 체결   → 통장
3. VALUATION   결과 장부를 평가                  → 통장
4. COMPLIANCE  committed 계좌를 관측             → 게시판
5. DECIDE      전략 시계가 이 시각에 걸렸으면    → 주문
```

- **ACCRUE가 EXECUTE 앞인 이유**: 배당·이자·대차수익·funding은 과거 보유 기간에 대한 대가다. 이번
  시각에 체결된 것은 아직 그 기간을 보유하지 않았다.
- **DECIDE가 마지막인 이유**: 방금 평가된 장부를 봐야 한다. COMPLIANCE와 DECIDE 사이 순서는
  correctness상 자유이나(둘 다 계좌를 바꾸지 않는다) 결정성을 위해 고정한다.
- `execution_time > decision_time`은 그대로 유지된다. 한 시각에서 체결되는 것은 **그보다 이전의
  결정**이다.

### 3.2 전략 시계는 execution table에서 유도되지 않는다

시도했고 두 이유로 기각됐다.

**(1) 장 마감 후 공시 데이터를 못 쓴다.** 일간 데이터는 거의 언제나 장 마감 후에 나온다.

```text
D    15:30   장 마감.  execution row 있음
D    19:00   그 날의 데이터가 publish 된다
D+1  09:00   이제 쓸 수 있다
```

시각표가 시장 시계면 판단이 15:30에 돌고, 그러면 볼 수 있는 최신 데이터는 **D-1의 19:00**이다.
`D-1 데이터 → D 15:30 판단 → D+1 15:30 체결`로 **한 칸이 통째로 낭비된다.** 독립 agenda면
`D-1 데이터 → D 09:00 판단 → D 15:30 체결`이다. 이것은 특수 상황이 아니라 일간 전략 전부에 걸린다.

**(2) 격자를 공유하면 느린 전략이 비용을 문다.** 프로젝트에 1분 execution table을 등록하면 월 1회
전략도 97,500번 불린다. 재사용을 장려하는 설계가 재사용을 벌주게 된다.

### 3.3 날짜는 유도해도 되고, 시각은 안 된다

```text
날짜를 유도한다     1분 테이블 → 거래일 250 개.  일별 테이블 → 거래일 250 개.  밀도 무관   허용
시각을 유도한다     1분 테이블 → 97,500.  일별 테이블 → 250.  밀도가 바꾼다              금지
```

`UC-TIME-002`의 보장 — *"denser execution table을 추가해도 frozen callback occurrence 집합이 변하지
않는다"* — 는 **날짜 유도에서는 유지된다.** `UC-CALENDAR-001`이 은퇴시킨 것은 시각 유도이며, 그 은퇴
사유는 날짜에는 적용되지 않는다.

따라서 별도 거래일 캘린더 dataset을 만들지 않는다. **execution table에 행이 있는 날이 거래일이다.**

### 3.4 agenda 어휘

`every`·`from`·`to`·`at`을 전부 갖는다. 얼리려면 다 알아야 한다.

```text
선언 (사람이 쓴다)      거래일 필터 + 하루 안의 규칙
        ↓  preflight 가 execution table 의 거래일 위에서 전개
resolved occurrences    시각 + 안정 ID 의 유한한 순서
        ↓  identity 해시가 run 에 각인된다
얼린 시각표             이후로는 이것만 소비한다
```

PRD §3.1의 핵심 단어는 *"resolve된"*이다. **요구는 run 시작 시점에 완전히 결정되어 있는 것이지,
사람이 목록을 타이핑하는 것이 아니다.** cron·RRULE·calendar inference를 거부한 이유는 규칙이 싫어서가
아니라 **패키지가 시장 사실을 추측하기 때문**이었다. 거래일은 데이터가 답하고 하루 안은 산술이므로,
어느 쪽도 추측이 아니다.

### 3.5 체결 시각 어휘

**기본: 결정 이후 첫 시장 시계 점.** 그 위에 선택적 손잡이 셋.

```text
at       하루 중 시각으로 후보를 좁힌다        1분 격자에서 종가 체결을 원할 때
after    최소 경과                             지연 체결
within   최대 허용 간격.  넘으면 실패          "당일에 못 채우면 실패"
```

`SAME_DAY`/`NEXT_ELIGIBLE` 열거와 `local_time`+`timezone` 조합은 사라진다. 둘의 차이(*"놓쳤을 때 다음
날로 넘기나"*)는 `within`이 흡수하고, *"오늘 15:20이냐 내일 15:20이냐"*는 "결정 이후 첫 번째"가
자동으로 가른다.

**이 어휘가 매 분 체결을 표현한다** — `at`을 비우면 후보가 격자 전체가 되고, 결정 이후 첫 점이 곧
다음 분이다. 그 외의 것(동일 시각 우선순위, 최소 간격, pending 교체)은 이미 옳게 되어 있었다.

## 4. 배선표 — 이것이 아키텍처다

```text
역할            시계        받는 View                         답의 수신자
───────────────────────────────────────────────────────────────────────
DataModel       전략 시계   창                                 창고
StrategyModel   전략 시계   창 + 계좌 + 이력                   주문 → Exchange
Accrual         시장 시계   보유 + 창                          통장       (자리만, §7.3)
Exchange        시장 시계   주문 + 시장상태 + 계좌 + 종목사전   통장
Compliance      시장 시계   창 + committed 계좌                게시판
```

**이 표는 프레임워크가 소유하고 닫혀 있다.** 확장점을 하나 더 만들려면 배선을 하나 더 만들어야 하고,
배선은 시계와 수신자를 정하는 일이라 프레임워크의 결정이다. §10.2가 *"확장점은 넷이다"*라고 닫아
놓은 것의 진짜 이유가 이것이다.

### 4.1 역할이 서로 다른 것은 둘뿐이다

받는 것과 주는 것은 "언제 불리는가"에서 유도된다. EXECUTE 자리에 불리면 주문을 받고 체결을 돌려주는
것 외에 할 일이 없다. 그래서 **다른 것은 딱 둘 — 언제 불리는가, 답을 누가 받는가.**

### 4.2 base는 얇다

```text
Role
   무엇을 구독하나       다섯 다 있다
   무엇을 기억하나       다섯 다 있다
   콜백 하나             (View) → Judgment.  다섯 다 하나씩

배선(시계 · 수신자)은 base 에 없다.  표가 갖는다
```

현재 `Component`가 어색했던 이유가 여기서 설명된다 — **추상 콜백이 없는 base**였다. 그것은 잘못이
아니라 정답이었고, 문제는 실제 공통 개념(배선표)이 코드가 아니라 문서에 있었다는 것이다.

### 4.3 부품과 도구

기준은 하나다. **자기 시계를 선언하는가.**

```text
부품    시계를 선언한다.  run 당 하나        DataModel · StrategyModel
도구    시계가 없다.  남의 시계에 붙는다     Exchange · Compliance · Accrual
```

**부품 = 도구 + 시계.** 상속으로 표현하면 이 방향이지, 다섯을 평평하게 두는 것이 아니었다.

## 5. 목적지는 셋이다

```text
창고 (DATASET)      다음 run 의 재료가 된다.  writes 로 이름을 선언한 것만
통장 (LEDGER)       계좌를 바꾼다.  Exchange 와 Accrual 의 답
게시판 (EVIDENCE)   아무것도 바꾸지 않는다.  관측 · 진단
```

**상태를 쓰는 것은 Account 하나뿐이다.** 도구는 전부 질의이고, 아무도 스스로 통장을 건드리지 않는다.
통장으로 가는 답이 하나가 아니라 둘이라는 것이 오히려 **"누가 append를 허가하는가"가 독립적으로
존재해야 함**을 드러낸다.

### 5.1 통장은 append-only 원장이다

현재 `AccountState`는 원장이 아니다. `snapshot`이 진실이고, `fill_history`는 발행 후 버려지며,
`mark_history`는 `retained_marks`만큼만 남는다. **진짜 원장은 record의 parquet 테이블이고,
`AccountState`는 원장의 캐시된 fold + 발행 대기 버퍼다.**

그 어긋남이 비용을 만든다.

- `_appends_one_mark`가 retention을 감안해 tail을 비교해야 한다. 진짜 append-only면 필요 없다
- `AccountState.__post_init__`이 매 전이마다 전체 이력의 단조성과 NAV 항등식을 O(n)으로 재검증한다
- `Prepared*` 세 타입이 각자 "무엇이 안 변해야 하는가"를 손으로 쓴다
- `fill_history: tuple[object, ...]` — 원장이라면 가장 타입이 강해야 할 자리에 타입이 없다

```text
Ledger      append-only 사실의 열 + 증분 fold
Account     권한.  "이 항목을 이 원장 뒤에 붙일 수 있는가" 만 판단하고 붙인다
```

**성능 이득은 없다.** fold는 지금도 증분이고 앞으로도 증분이다. 얻는 것은 불변식이 세 벌에서 한
벌이 되는 것이다. 그리고 **죽은 run이 남기는 것이 손상된 계좌가 아니라 짧은 이야기가 된다** —
append-only 자료구조에는 중간 상태가 없고 모든 앞부분이 유효한 원장이다. 이것이 run을 한 종류로 둘
수 있는 이유이기도 하다.

### 5.2 원장 항목은 한 모양이다

`TradeEvent | CashFlowEvent | PositionAdjustmentEvent` 같은 합타입은 과하다. 분류 기준이 "무엇이
변하나"인데 그것은 통장이 이미 아는 것이다.

| | Δ현금 | Δ수량 |
|---|---|---|
| 체결 | 있다 | 있다 |
| 배당(현금) · 대차수익 · funding · 선물 정산 | 있다 | 없다 |
| 액면분할 · 무상증자 | 없다 | 있다 |
| 펀드 설정 · 환매 | 있다 | 없다 |

전부 같은 두 칸의 조합이다. 그래서 **한 모양 + 출처 태그**로 족하다.

```text
LedgerEntry
    at          시각
    cash        Δ현금
    positions   {종목: Δ수량}
    origin      무엇이 이걸 만들었나
    detail      출처별 상세
```

```text
통장이 검사하는 것       append-only · 버전 순서 · 결과 상태가 유효한가
통장이 검사 않는 것      "가격 x 수량 = 현금" 같은 출처별 불변식.  만든 쪽이 검사한다
```

통장이 체결의 불변식을 알면 통장이 체결을 알게 되고, 그러면 상품군마다 통장을 고치게 된다.

### 5.3 왜 Fill-only가 안 되는가

배당을 `side=BUY, quantity=0, price=0, cost=-배당금`으로 인코딩하면 계좌의 숫자는 맞지만 **증거가
오염된다** — 체결 건수, 회전율, 체결 비용 분석, fill rate가 전부 거짓이 된다. §2.4가 네 단계를 나눈
이유가 각 단계의 숫자가 서로 다른 것을 뜻하기 때문인데, 배당은 그 사슬을 하나도 지나지 않는다.

## 6. Exchange

### 6.1 계약은 좁다

```text
받는다    주문 배치
          그 시각의 시장 상태          execution table 스냅샷
          계좌 스냅샷
          주문에 등장하는 종목의 정체   Instrument 사전

준다      체결 결과                    수량 · 가격 · 비용 · 미체결이면 그 사유
```

**어떻게 채우는지는 전부 venue 내부다.** 프레임워크가 단계를 고정하지 않는다.

단계를 고정하려 했다가 기각됐다. 선물(승수·일일정산·증거금·만기), 중국 A주(T+1 — 계좌 이력에 의존),
채권(경과이자), 옵션(만기 정산)에서 깨진다. 여럿이 **주문 → 체결 밖의 일**을 하므로, 단계를
프레임워크가 정하면 담을 수 없는 venue가 반드시 생긴다.

규칙 on/off는 **venue의 설정**이다. 스키마는 venue가 정의하고, 프레임워크는 *"venue는 설정을 갖는다"*만
안다. `references`의 KRX 프로파일이 *"구현함 / 구현 안 함"*을 docstring에 적고 있다는 것이 신호였다 —
코드가 표현해야 할 것이 산문으로 밀려나 있었다.

### 6.2 종목 선언 — 세 집합이 독립이다

```text
execution table     3,000 종목 (주식 + ETF)
instrument 선언       200 종목 (주식만)
실제 주문              30 종목
```

**요구되는 포함관계는 둘뿐이다.**

```text
주문 ⊆ 선언       venue 가 정체를 알아야 세금 · 승수를 결정한다
주문 ⊆ 테이블     가격을 알아야 체결한다
```

선언과 테이블 사이에는 아무것도 요구하지 않는다. ETF가 테이블에 섞여 있어도 주식만 선언하고 주식만
주문하면 그대로 돈다.

두 반대안이 왜 틀렸는지가 이유다. 모든 테이블 종목 등록을 요구하면 쓰지도 않을 3,000개를 선언해야
한다. 아무것도 요구하지 않으면 venue가 추측하고, 그 결과가 `docs/issues/archive/007`
(*"an undeclared instrument is silently a share"*)이다.

### 6.3 검사가 두 시점으로 갈린다

```text
preflight    선언이 하나라도 있는가?  0 개면 어떤 주문도 성공할 수 없다.  돌 이유가 없다
runtime      이 주문의 종목이 선언됐는가?  미등록이면 run 실패
```

어느 종목에 주문이 나갈지는 전략이 판단해 봐야 알기 때문에 preflight가 잡을 수 없다. **미등록은
경제적 사실이 아니라 설정 오류이므로 typed zero-dealt로 넘기지 않고 실패한다.** 다만 실패할 때
미등록 종목을 하나가 아니라 **전부 모아서** 보고한다.

### 6.4 Instrument 사전은 창고가 아니다

```text
창고    시간축이 있는 것.  창으로 읽는다
사전    시간축이 없는 것.  통째로 읽는다
```

`kind`·`currency`는 시점에 따라 변하지 않고(§2.8) PIT 창으로 읽지 않는다. 창고에 넣으면 *"이 종목이
언제부터 ETF였나"* 같은 없는 질문이 생긴다.

## 7. Constraint · Compliance · Accrual

### 7.1 Constraint는 확장점이 아니다

**개념은 존재하되 built-in으로만 제공한다.** 사용자가 제약을 걸고 싶으면 콜백 안에서 직접 한다.

```python
desired = signal_weight(signal)
lo, hi = no_short(call.instruments)
lo, hi = intersect(lo, hi, single_name_cap(call.instruments, bench, cap))
return Rebalance(optimize(desired, lo, hi))
```

이것이 PRD §7을 현재 구현보다 정직하게 읽는다. §7은 *"구성은 best effort, monitoring은 사실 관찰"*
이라고 적었다. **best effort는 재량이고 재량은 전략의 것이므로 프레임워크가 보장할 것이 없다.**
사실 관찰은 프레임워크가 보장해야 하므로 확장점으로 남는다.

부수적으로 정직해지는 것이 있다. `single_name_cap`이 벤치마크 비중을 읽으려면 **전략이 그 데이터를
구독해야 한다.** 지금은 constraint의 requirement 안에 숨어 전략의 데이터 의존성이 보이지 않았다.
`UC-CONSTRAINT-002`의 보장(*"binding이 없으면 결과를 만들기 전에 실패"*)은 유지된다 — 데이터가 없으면
호출이 실패하고, 콜백 실패는 PRD §3.6에 따라 원자적이다.

**잃는 것**: §7.1이 요구하는 *"constraint별 before/after와 잔여 보존"*이 프레임워크 보장에서 전략이
직접 기록하는 것으로 내려간다.

### 7.2 Compliance

```text
Compliance   시장 시계 위, VALUATION 직후
             구독한다 · 기억한다 · committed 계좌를 관측한다 · finding 을 남긴다
             계좌를 바꾸지 않는다 (PRD §6.8)
```

memory가 여기 있는 이유는 명확하다 — *"세 번째 위반이다"*, *"연속 5일 초과 중"*. **위반은 세는 것이고
세는 것은 기억한다.**

`Constraint`의 두 멤버를 쪼개는 근거는 셋이다.

1. **memory의 의미가 각각 명확해진다.** bound 계산은 대개 무상태이고, 관측은 센다
2. **관측만 하는 것이 표현된다.** 지금은 관찰하려면 `project`도 구현해야 한다
3. **서로 다른 시계 위에 산다.** bound는 전략 시계, 관측은 시장 시계

**소유자 결정: 전략이 쓴 값과 Compliance가 재는 값을 맞추지 않는다.** 감시자가 감시 대상의 목표를
물려받으면 감시가 아니라 자기채점이다. §7.1이 *"같은 판단을 두 번 채점하면 두 채점이 갈릴 수 있고,
그때 어느 쪽이 사실인지 말할 방법이 없다"*고 한 것이 그 얘기다. 둘이 다른 것이 정보이며, 리포트에
나란히 남는다.

### 7.3 Accrual — 자리만

배당 · 대차거래 수익 · crypto perp funding fee · 선물 일일정산 · 펀드 설정/환매가 갈 자리다.
**MVP 범위 밖이며 이 문서는 자리와 배선만 확정한다.**

이것들이 데이터가 아니라 계산인 이유: 배당락일에 인식하나 지급일에 인식하나, 원천징수 세율은,
재투자하나 — **전부 경제적 선택이고 프레임워크가 정하면 안 된다.**

`origin`을 구조화하지 않는다(소유자 결정). 다만 펀드 설정/환매는 NAV의 분모를 바꾸므로, 시간가중
수익률이 필요해지는 시점에 *"외생적 현금흐름인가"*가 구조적으로 필요해질 것이다. 그때 다시 본다.

## 10. 아직 안 정한 것

1. **패키지 이름과 배치.** 무엇을 하는지가 아직 안 끝났으므로 이름부터 정하지 않는다. 캠페인
   Stage 4가 끝난 시점에 결정한다.
2. **배선표의 코드 모양.** 표를 데이터로 둘 것인가, 타입으로 둘 것인가.
3. **`writes`가 하나인가 리스트인가.** run이 전략 하나가 되면서 하나로 충분해 보이나, DataModel이
   한 번의 계산으로 여러 dataset을 내는 경우가 남는다.
