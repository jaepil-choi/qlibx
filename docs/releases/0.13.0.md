# vqapr 0.13.0 — a run holds its horizon once, and a batch bakes each dataset once

Released 2026-09-10 from `develop`. The one-cube campaign
(`docs/refactoring/2026-09-10-the-one-cube-campaign.md`, records `235`–`236`) closes
`docs/issues/098`: a datamodel run's memory tracked its instrument count and not its period.
Nothing breaking: no registered document or record changes shape; the store and the workers
take new keyword arguments with defaults.

## 1. A panel is the run's horizon, and a numeric field is held once (record `235`)

- The panel behind `read(alias, field)` is scanned from the earliest instant any lookback the run
  declared on that dataset reaches at `start`, up to `end` — not over the registered span. A
  one-year run over a ten-year source holds one year plus its lookback.
- A numeric field is one `(instants × instruments)` float64 matrix; `matrix()` is a view of its
  rows. The Arrow copy and the validity bitmap that sat beside it are gone. `values[name]` and
  `series` still hand `None` where absent and `int` for an INTEGER field; a string or date field
  stays an Arrow array.
- A window the panel never read — a cutoff past the run's end, a calendar bound below the scan's
  lower bound — is refused (`RuntimeError`) rather than silently shortened.

## 2. A `--jobs` batch bakes each dataset once, and every worker maps it (record `236`)

- Before the workers start, `vqapr run a b c --jobs N` scans each panel-grain dataset the runs
  read once, over **every** instrument the source holds and the registered span, into
  `.vqapr/cubes/<batch>/<dataset_id>/`: one memory-mappable `.npy` per numeric field, plus the
  instant axis, the instrument axis, and where a source row existed.
- Each worker takes its panel as a slice of those files. A run over the whole universe gets a
  view — the OS page cache holds the bytes once per machine for every worker; a run over a subset
  gets one gather the size of what it declared. The panel is the one a scan would have built,
  cell for cell.
- The directory is removed when the batch returns — on success, refusal or exception. A directory
  a hard-killed driver left behind is swept by the next batch once its lock is stale (10 minutes
  without the driver's 30-second heartbeat). Nothing accumulates; a single run (`vqapr run x`)
  scans as before.
- What cannot be baked (an unverified registration, a non-numeric field, a `rows` grain, a source
  that will not scan) is simply absent; that worker scans and refuses by name as it does outside a
  batch. A cube is used only when its recorded source digest matches the bytes the worker verified.

## 3. What memory scales with, said where a reader sizes a sweep

`make-datamodel/references/reading-inputs.md` and `run-backtest/SKILL.md` §5 now say it: per
numeric field, one matrix of (period + longest lookback) × declared instruments, once and shared
under `--jobs`, on top of about 130 MB of interpreter per worker. Size `--jobs` by memory per
worker, not by core count. `skill install` will report both files `outdated` on a 0.12.0 install
and update them.

## Measured

`experiments/exp_236_the_panel_memory/`, a synthetic source of the reported shape (4,975 names,
2,955 sessions, 8.0M rows, 407 MB), one field, 160-day `CalendarLookback`, 7-year run, worker in
a fresh process (interpreter floor 0.13 GB):

| worker | names | panel build | private memory | peak |
|---|---|---|---|---|
| 0.12.0 (scan, registered span) | 309 | 0.7 s | +0.04 GB | 0.18 GB |
| 0.13.0 scan (single run, horizon) | 309 | 0.58 s | +0.074 GB | 0.17 GB |
| 0.13.0 cube (under `--jobs`) | 309 | 0.29 s | +0.007 GB | 0.17 GB |
| 0.13.0 scan (single run, horizon) | 4,975 | 1.30 s | +0.372 GB | 0.76 GB |
| 0.13.0 cube (under `--jobs`) | 4,975 | 0.30 s | +0.013 GB | 0.17 GB |

The bake itself: 1.6 s and 132 MB on disk per field over all 4,975 names, once per batch. A
671-run sweep that made 671 scans makes one.

## Migrating a 0.12.0 tree

Nothing to do. Registered datasets, run definitions and records are read as they are. An
in-process caller constructing `DuckDbObservationStore` directly gets the registered-span scan it
had unless it passes `horizon=` and `requirements=`.
