# vqapr 0.14.0 — one door from a declaration to a run, and a command reads each fact once

Released 2026-09-10 from `develop`. The one-door (run) campaign
(`docs/refactoring/2026-09-10-the-one-door-run-campaign.md`, records `240`–`241`) on top of the two
bounded fixes the 0.13.0 scenario traces led to (records `238`–`239`). Nothing changes shape: no
registered document, record or envelope key; every `check` and `run` envelope on the sample door
is byte-identical to 0.13.1's (`tests/characterization/check_and_run_envelopes.baseline.json`).
One behaviour changes, and it is a fix: a run in a `--jobs` batch is now judged.

## 1. One door: `verify_run` (records `240`, `241`)

- `flow/declaration/verify.py::verify_run(workspace, definition) -> RunVerdict` is the only path
  from a `RunDefinition` to a `FrozenRun`. `check` renders the verdict; `run`, `public.execute`
  and the `--jobs` workers call `require_frozen()` on it. The judgments (every question answered
  independently, for `check`'s "everything at once") and the freeze (names resolved to values,
  first refusal) keep their reporting shapes, but they no longer read the declaration twice.
- **`--jobs` workers make the judgments.** A worker used to freeze without asking them, so
  `vqapr run a b --jobs 2` ran what `check` and `vqapr run a` refused (`docs/issues/archive/015`,
  one door over). Each batch entry now carries `check`'s refusal in `check`'s code, and a refused
  run writes no record.
- **Each fact is read once per command** (`preflight.RunFacts`): the agenda, the execution table
  and its horizon, the loaded strategy/datamodel and venue. A fact that cannot be read raises the
  same exception to every judgment that needed it (`docs/issues/archive/077`) and to the freeze.
  `experiments/exp_238` had counted, per `vqapr run`, the execution table's instant column read
  five times and the strategy imported four; now one and two (the second is the fresh instance
  the initial memory is proved on, `docs/issues/archive/076`), then the run's own.

## 2. What the scenario traces led to (records `238`, `239`)

- `Workspace` reads a dataset's distinct instants once and hashes a source once per command --
  even when the digest compare fails. `ExecutionHorizon.between` cuts the horizon from instants
  already read. A `--jobs` driver asks each run what it reads once (`batch_reads`).
  `vqapr check` on the sample's three-year run: 182 → 97 ms in-process.
- A callback frames its memory once: `_candidate_callback_state` returns one
  `PreparedModelState`, and `RunStateRepository.prepare_callback(prepared=)` takes it without
  normalizing and hashing again. Refs and records are byte-identical (showcase digest 83/83).

## 3. `check` answers for an `end` between a day's fill and its decision (0.13.1, record `237`)

Carried in from 0.13.1: the ordering judgment asks about `inclusive_slice(start, end)`.

## Migrating a 0.13.x tree

Nothing to do. `preflight_run` and `judgments` keep their signatures (each gained an optional
`facts` argument). A caller that constructed `Workspace` objects and called
`flow.declaration.preflight.preflight_run` directly still gets a freeze; the judgments are made
by `verify_run` and by the public `preflight_run`.
