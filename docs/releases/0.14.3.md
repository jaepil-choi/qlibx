# vqapr 0.14.3 — a callback frames what it read once, the sessions are read for the run's period, and the heartbeat touches the lock once a second

Released 2026-09-10 from `develop`. The one-callback campaign
(`docs/refactoring/2026-09-10-the-one-callback-campaign.md`, records `246`–`248`), the fixes the
0.14.2 scenario traces led to (`experiments/exp_246_the_scenario_trace_0_14_2/`). Nothing changes
shape: no registered document, record or envelope key; the sample door's eight `check` and `run`
envelopes are byte-identical to 0.14.2's (`tests/characterization/check_and_run_envelopes.baseline.json`)
and every showcase record digest matches (83/83). No behaviour changes.

## A callback frames what it read once (record `246`)

The intent's source refs and the evidence's were derived twice per callback from the same
window, and the Strategy's `inputs()` was asked again on every decision. `CallbackHandler` resolves
the declaration once per run (as `ComputeHandler` already did) and frames the source refs once after
`decide`, handing them to the stamp and to the evidence. Per ten-decision run: 20 → 10 framings,
15 → 6 askings.

## The sessions are read for the run's period (record `247`)

`Workspace.evaluation_times` read a dataset's whole instant column and cut it in Python; a
ten-session run over a three-year table read 735 instants to keep ten. `scan.distinct_values` takes
inclusive bounds and the workspace reads `[start − 1 day, end + 1 day]` for the agenda and the
horizon alike; both cuts are unchanged. The bounds are `TIMESTAMPTZ` literals in the statement,
because binding a tz-aware datetime as a parameter costs a process its first ~450 ms.

## The heartbeat touches the lock once a second (record `248`)

The run lock's mtime is the heartbeat (`LOCK_STALE_AFTER` is two minutes); the writer touched it on
every record chunk — 110 times for a ten-decision run, 404 for thirty-seven — and on a network home
each touch is a round trip. `LOCK_TOUCH_EVERY = 1.0`; `progress.json` keeps its own cadence.

## Looked at and left alone

- The exchange's memory framed at every fill: the venue ran at that instant, so it is the
  contract, not a repeat.
- `verify_roster` at run start (350–400 ms): the cost is the process's lazy `import
  pyarrow.parquet`, which the first record chunk would pay instead; reading the roster fresh every
  run is issue 009's design.
- `_as_loaded_fingerprints` hashing the strategy and venue files again at run start: record 242's
  decision.

## Migrating a 0.14.2 tree

Nothing to do. `scan.distinct_values` and `Workspace.evaluation_times` gained keyword-only
optional arguments; every existing call is unchanged.
