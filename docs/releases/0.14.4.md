# vqapr 0.14.4 — month-end agendas, a batch that writes its run records, a strategy run that does not grow with its fills

Released 2026-09-11 from `develop`. Seven of the nine 2026-09-11 testbed reports (0.14.2 wheel: the
A/B testbed, the FF3 testbed and enhanced-index-3), closed on the owner's instruction by records
`249`–`257`, and the skill work another session landed beside them (the entry skill, factor
portfolios, analyze-result). One addition to a declaration — `agenda.on` — and no key removed or
renamed; a run that does not say `on` stores and freezes exactly as it did.

## An agenda can fire on the last trading day (record `253`)

`every: 1M` fired only on a month's first trading day, and three agents given "rebalance on the last
trading day of each month" declared it three different ways. `on: last` fires a `w` or `M` rule on the
last trading day of each week or month:

```yaml
agenda:
  every: 1M
  on: last
  at: "15:29"
```

A month counts once the execution table shows it over: the run reads its sessions past `end` to find
the next one, fires on none of them, and a month the table stops in the middle of does not fire.
`on` is stored only when it is `last`, so every existing run keeps its identity.

## A `--jobs` batch writes the run record a single run writes (record `249`)

A batch reported every run completed and `list runs` listed them, but `show run` and
`strategy_report` refused each one: the workers never wrote `run.json`. It is now written by the
member body both paths pass. A run already executed in a batch gets its record by running it again
with `--force`.

## A strategy run's memory no longer grows with everything its fills produced (records `254`–`257`)

Measured on a synthetic 300-name daily book trading every name every session, same machine, old and
new code alternating: **1.94 → 1.43 GB** peak private at 300,000 fills, wall time unchanged.

- The run's envelope and the published `writes` dataset read the record a batch at a time (`254`);
  every fill row became a Python dict after the run, and that was the peak.
- The end of a run folds spilled parts into `all.parquet` a row group at a time (`255`); it read them
  back whole, so the 256 MB spill raised the peak it exists to bound.
- A run with a record keeps what its fills produced in the record, not in memory (`256`).
- A `--jobs` worker starts with one BLAS thread unless you set a count (`257`): numpy's OpenBLAS
  commits a buffer per core when it loads — 0.84 GB private per process on a 32-core machine, 0.06 GB
  with one thread.

## Smaller fixes

- A usage refusal names the form the command accepts and what it refused (record `250`):
  `vqapr new instruments A B` is refused as `vqapr new`, with its usage line and `vqapr new --help`,
  and `observed` is `B`.
- `vqapr new strategy --calendar-lookback DAYS` scaffolds a `CalendarLookback` with the guard that
  window implies (record `251`); `--instants-lookback` on a strategy is a 400 refusal, not a 500.
- `vqapr register strategy <id> <file>` finds a leaf that inherits `StrategyModel` through an
  imported base, as the YAML route does (record `252`). A component that imports a module beside it
  is still refused — a component is one file, and its fingerprint covers that file alone — and the
  `fix` now says so; make-strategy and make-datamodel say it too.

## Migrating a 0.14.3 tree

- Nothing to do for a project, a registered document or a record.
- A Python caller that runs with a `store_root` and reads fill-side evidence from the in-memory
  result — `final_state.feedback`, the `detail` of a lifecycle entry that is not a decision, a market
  trace's `post_account_result` — finds it gone: those are the record's `vqapr.fill`,
  `vqapr.account` and `vqapr.monitoring` rows. `callback_evidence(result)`, the lifecycle kinds,
  `report` and `monitoring` on every trace are unchanged, and a run without a `store_root` keeps
  everything.
- A declaration using `on: last` is refused by an older vqapr (the key is unknown to it).
