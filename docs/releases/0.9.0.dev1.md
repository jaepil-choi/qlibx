Built 2026-09-09 from `develop`. Record `199`. **Not published to an index** — this build exists
to be installed into the testbeds from `dist/`.

`0.9.0.dev0` carried the layering campaign (records `190`–`198`): the package import graph is a

## The one change: a tenth skill, `report-issue-dev`

`vqapr skill install` now writes ten directories instead of nine.

The nine are divided by what the user came to do — register data, write a strategy, read a result.
The tenth has a different subject: **vqapr being wrong**. It files a defect or friction report
about the package itself into the upstream repository's `docs/issues/`, as one dated Markdown file.

It exists because the reports worth the most were the ones most likely to be lost. A testbed agent
has the installed public surface and nothing else, which is exactly why its findings are evidence —
issues `055` and up all came from that position, and the heaviest of them are heavy because
someone without the implementation could not get past them. Filing them had no mechanism: the
instruction that existed named no destination, no required content and no reader, so reports landed
in whatever file each testbed happened to have, and two of those were reset between runs.

**What a report must carry.** The vqapr version, read from the package rather than recalled
(`vqapr skill list` reports `package_version`; `uv pip show vqapr` reports the wheel), and the
failing command's entire refusal envelope pasted verbatim. Then scenario, expectation with its
source named, what happened, reproduction with a count, impact including any workaround, and what
would have prevented it. `references/report-template.md` is the skeleton and one filled example.

**When to file.** `references/what-counts-as-a-defect.md` turns `status` into the decision it
already is: **500 and 502 always**, **423 and 503 never** (retry unchanged), the 4xx family only
when `fix` did not fix or named something absent. Also worth filing: two parts of the package
disagreeing, a number that is wrong, and friction — friction **before** you resolve it, because
once you know the answer you can no longer see what was missing.

**Two rules the skill holds to.**

- **No number.** Reports are `report-YYYY-MM-DD-<slug>.md`. `NNN-` names belong to issues the owner
  has triaged and `src/` cites them as decision authority; two testbeds filing at once would also
  collide on the same next integer.
- **Write-only upstream.** Opening upstream `src/`, `tests/`, `docs/` or the existing issues to
  diagnose is forbidden. A finding contaminated by the implementation is no longer evidence about
  the public surface, and nothing downstream can detect that it happened.

If no upstream checkout is on the machine — any real user — the skill writes to `vqapr-reports/`
in the project instead and says so.

`introduce-vqapr` routes to it, and its "Friction logging" section now names it rather than
describing a log with no destination.

## Upgrading

```bash
uv run vqapr skill install          # both targets; --dry-run first to see what changes
uv run vqapr skill list             # ten available
```

`skill list` reports each file as `current`, `outdated` (an earlier release's copy, updated
silently) or `modified` (differs from every release vqapr has shipped, so `--force` is required to
overwrite). `introduce-vqapr/SKILL.md` changed in this build and will read `outdated` on a
0.9.0.dev0 install.
