## 1. 한 장 요약

### 1.1 고리 하나

vqapr이 하는 일은 고리 하나다.

> 등록된 데이터에서 **그 시점까지 알 수 있던 것만** 전략에게 보여 준다. 전략이 목표 포트폴리오를 정하면,
> 거래소가 수수료 · 매도세 · 1주 단위 · 거래정지를 반영해 체결하고, 계좌가 그 체결을 원장에 붙이고 평가한다.
> **다음 판단은 그 계좌를 보고 한다.**

이 고리는 **시계 두 개**가 돌린다.

```text
일정 시계 (schedule)   사용자가 선언한 판단 시각. "매일 08:00", "매월 첫 거래일 09:00"
                       전략(또는 DataModel)이 부르는 시각이다
시장 시계 (market)     체결표(execution table)가 run 기간 안에 가진 모든 시각
                       체결되고, 평가되고, 감시받는 시각이다
```

한 시장 시각에서 일어나는 일의 순서는 고정이고, 코드에서 **한 곳, 다섯 줄**에만 적힌다.

```python
at = accrue(at)    # 1. 지난 보유 기간이 번 것 (배당 · 쿠폰 · 이자 · funding) → 원장   (지금은 자리만)
at = execute(at)   # 2. 이 시각이 목표인 대기 의도를 체결                        → 원장
at = value(at)     # 3. 결과 장부를 평가                                         → 계좌의 평가
at = observe(at)   # 4. Compliance 규칙이 committed 장부를 본다                   → 증거
at = close(at)     #    체결의 뒷정리 (피드백 증거)
# 5. 같은 시각에 일정 시계의 판단(DECIDE)이 걸려 있으면 그것은 별도 사건이고, 위 다섯 줄 뒤에 온다
```

루프는 두 시계의 사건을 시간순으로 섞어서 하나씩 처리하는 것이 전부다.

```python
for event in sorted(events, key=sort_key):   # ScheduledEvent 와 MarketEvent 를 시간순으로
    handle(event)                             # ScheduledEvent → 부품(decide/compute), MarketEvent → 위 다섯 줄
```

두 시계는 run이 시작하기 전에 전부 알려져 있다. 그래서 같은 입력은 같은 사건 목록을 만들고, 같은 결과를 낸다.
vqapr의 루프는 **이산 사건 시뮬레이션(DES)** 이다 — 사건 목록 전체를 미리 알고 시각 순서대로 처리한다.
발행/구독으로 사실을 흘려보내는 event-driven architecture가 아니다. 그래서 어휘도 DES의 것을 쓴다(§3).

### 1.2 그림 위의 폴더

```text
 등록된 데이터 (그 시점까지만)         data/
        │ 창                           data/window.py · data/panel.py
        ▼
 전략 — 판단                          component/strategy/   (사용자가 구현하는 계약)
        │                              signals/ · portfolio/ (저자가 부르는 순수 함수)
        │ 목표 포트폴리오               domain/intent.py
        ▼
 체결 — 주문 계획 → 거래소             domain/order.py (plan_orders) · component/exchange/
        │ 체결                          domain/fill.py
        ▼
 계좌 — 원장에 붙이고 평가             domain/account.py · domain/valuation.py
        │                              (옆에서 component/compliance/ 가 본다)
        │ 스냅샷
        └──────────▶ 다시 전략

 고리를 돌리는 것      run/engine/        loop.py · stages/{decide, compute, accrue, execute, value, observe}.py
 고리 밖 — 출발 전     workspace/ · run/preflight/
 고리 밖 — 도착 후     run/recording.py · record/ · report/
 고리 밖 — 표면        public.py · cli/ · agent/
```

**박스는 폴더이고, 박스 사이를 오가는 값은 `domain/`에 있다.** 한 개념은 한 모듈이고(§5), 사용자가
확장하는 네 역할은 한 추상화(`component/`)의 네 모습이다(§4).

### 1.3 세 줄 규칙

1. **아무도 데이터를 직접 열지 않는다.** 소비자는 무엇을 읽을지 선언하고(`inputs()`), 엔진이 그 시점까지로
   잘린 창을 건넨다.
2. **계좌(`Account`)만 상태를 쓴다.** 나머지는 전부 값을 계산해 돌려준다.
3. **컴포넌트는 서로를 부르지 않는다.** 다음 단계를 부르는 것은 엔진이다.

### 1.4 이 문서가 0.15.0과 다른 점

0.15.0의 설계(archive)는 옳은 경계를 여럿 세웠다 — 시계 둘, 배선표, 한 문(one door), append-only 원장. 그런데
**폴더는 import 고도(층 번호)로 갈렸다.** "두 패키지가 주고받는 값은 `domain/`에 둔다"는 순환을 없애기 위한
규칙이 개념을 흩었다: 계좌 하나가 네 패키지의 여덟 파일에, 컴포넌트 역할 하나가 예닐곱 패키지에 있었고,
같은 파일 이름 아홉 쌍이 서로 다른 뜻이었다.

이 문서는 같은 경계를 지키면서 **폴더를 개념과 Component 추상화로 다시 가른다.** 바뀌지 않는 것:
고리와 그 순서, 한 문, 판정과 얼리기, 원장, 기록, 그리고 **run이 계산하는 숫자**. 바뀌는 것: 어디에 있는가와
무엇이라고 부르는가. 공개 어휘가 바뀌는 곳(§3의 `schedule`/`ScheduledEvent`, §12의 단일 저자 표면)은 한 번의
깨지는 릴리스에 묶는다.

## 2. 설계 원칙

### 2.1 목표 한 줄 — 모든 숫자의 출처

> **모든 숫자에 대해 "이것이 어디서 왔는가"에 답할 수 있는 시뮬레이터.**

PRD의 규칙은 전부 이 한 문장을 지키는 장치다.

| PRD | 지키는 것 |
|---|---|
| §2.2 하나의 execution spine | 수익의 출처가 하나다 |
| §2.4 committed state만 authority | 상태의 출처가 하나다 |
| §2.3 값과 배분은 다른 역할 | 의미의 출처를 섞지 않는다 |
| §3.2 PIT | 정보의 출처가 시간상 정당하다 |
| §2.5 durable typed artifact | 산출물의 출처를 검사할 수 있다 |
| §10.2 explicit failure | 없는 것을 추측으로 메우지 않는다 |
| §9.4 intended와 realized | 의도와 사실을 구분해서 남긴다 |

**수익을 주장하는 모든 것은 한 경로를 지난다**: 판단 → `plan_orders` → `Exchange.execute` → `FillBatch` →
`LedgerEntry` → `Account.append` → `Account.mark`. 이 경로를 지나지 않고 수익 · NAV · PnL · 회전율을 만드는
코드는 없다(PRD §2.2). **DataModel은 이 경로에 들어오지 않고, StrategyModel은 반드시 지난다** — 이것이 두 역할을
가르는 기준이다(PRD §2.3).

### 2.2 제어의 역전 — 누가 무엇을 소유하나

| 소유자 | 소유하는 것 | 소유하지 않는 것 |
|---|---|---|
| **엔진** (`run/`) | 일정 전개와 얼리기 · 두 시계의 병합 · 한 시각의 순서 · bounded Call 주입 · 콜백 결과 검증 · **판단 시각 도장**(현재 사건의 시각, 덮어쓸 수 없다) · 원자적 수락 · 체결로의 연결 | 경제 규칙. 전략의 cadence 해석 |
| **부품** (DataModel · StrategyModel) | 자기 시계(`schedule`)와 경제적 cadence · warm-up · cooldown · 지금 판단할지 · 무슨 의도를 · 어떤 상자 안에서 | 판단 시각 · 체결 목표 |
| **도구** (Exchange · Compliance · Accrual) | 자기 판단 하나 | 시계. 배선표가 정한 시장 시각 자리에 불린다 |
| **`FillRule`** | 도장 찍힌 판단 시각 뒤의 정확한 체결 목표 | — |

- 엔진은 반복 규칙이나 달력을 해석하지 않고, 체결표의 행에서 **판단 시각**을 만들지 않는다(날짜만 유도한다, §3.2).
- 전략은 미래의 일정도, 체결표의 행도 보지 못한다.
- 일정은 **판단의 기회** 목록이지 판단 목록이 아니다. 콜백은 `Hold`를 돌려줄 수 있다.

**없으면**: cadence가 엔진의 숨은 규칙이 되거나, 전략이 체결 시각의 사실을 판단에 쓰게 된다.

### 2.3 최소 권한 — 없는 길은 쓸 수 없다

규칙은 잊히지만 없는 것은 호출할 수 없다. 이 설계는 다섯 개의 **부재**로 경계를 지킨다.

1. **모델은 체결표에 닿지 못한다.** 모델의 데이터 경로는 창(`data/window.py`) 하나이고, 체결 스냅샷은 엔진의
   체결 단계만 만든다.
2. **DataModel은 계좌를 보지 못한다.** `DataCall`에 `account`가 없다.
3. **`signals/`와 `portfolio/`는 데이터 · 상태 · 시계를 보지 못한다.** 인자로만 받는다 — 시그니처가 계약이다.
4. **모델은 자기 상태를 commit하지 못한다.** `save_payload(target)`는 열린 target만 받고, 상태 참조는 엔진이
   발행한다.
5. **저장소 핸들은 소비자에게 가지 않는다.** 창을 만드는 엔진만 쥔다.

`store.query(...)` 한 줄이 look-ahead다. 백테스트에서 닿을 수 있는 것은 곧 보이는 미래다.

### 2.4 Aggregate root — 계좌

현금 · 보유 · 버전 · 원장의 쓰기 권한은 `Account` 하나에 있다(PRD §2.4). 계좌의 문은 둘 — **append**(원장
항목을 붙인다)와 **mark**(평가를 기록한다) — 이고, 계좌가 판단하는 것은 "이 항목을 이 원장 뒤에 붙일 수 있는가"
뿐이다(§9). intended ≠ requested ≠ dealt ≠ committed는 끝까지 구별되고, 의도한 값을 상태에 쓰는 경로는 없다.

### 2.5 Functional core, imperative shell

계산(가중 · 구성 · 주문 계획 · 체결 · 평가 산술)은 순수 함수다. 부작용(commit · 발행 · 상태 전달)은 엔진에만 있다.
계산이 순수하면 결정론적 재현이 공짜다 — fixture 테스트와 `UC-SCALE-001`의 동등성이 여기에 기댄다.

### 2.6 Profile은 주입한다

Academic과 KRX는 같은 생명주기에 다른 정책이다(PRD §6.4). run의 `exchange:`가 둘 중 하나를 주입하고,
**profile별 엔진은 없다.** 있으면 `UC-PORTFOLIO-001`이 두 코드 경로의 우연한 일치가 된다.

### 2.7 한 문 (one door)

같은 것을 확인하는 곳은 하나다.

| 문 | 무엇을 | 누가 지나나 |
|---|---|---|
| `data/verification.py` | 물리 파일을 **한 번** 잰다. 이후엔 지문만 대조한다 | 등록 · 재등록 · run 출력 발행 · 모든 읽기 |
| `run/preflight/verdict.py::preflight` | run 하나를 판정하고 얼린다. 사실은 명령당 한 번 읽는다 | `vqapr check` · `vqapr run` · Python `run` · `--jobs` worker |
| `component/conformance.py` | 컴포넌트가 약속한 모양인가 | 등록 · pytest. 출하하는 구현도 같다 |
| `workspace/registration.py` | 선언 문서 하나를 트랜잭션 하나로 | `vqapr register` · Python `register_*` |

**없으면**: `check`는 거절하는데 `run`은 돌리는 일(과거 이슈 015), 체결표를 한 명령에서 다섯 번 읽는 일이
생긴다.

### 2.8 명시적 실패

비슷한 필드, 이전 가격, 다른 비용 정책으로 조용히 대체하지 않는다(PRD §10.2, `UC-ERROR-001`,
`UC-COST-004`). 선언한 가격 컬럼이 없으면 실패하고, 등록 뒤 파일이 바뀌면 실패하고, 가격이 없는 보유는
만들어 낸 가격으로 평가하지 않는다.

### 2.9 DRY의 경계

DRY는 **같은 이유로 바뀌는 것**에 적용하지, 같은 모양에 적용하지 않는다.

```text
공유    PortfolioIntent · OrderBatch · FillBatch 봉투 · Account 의 두 문과 이력 · 사건 순서 · 실패 어휘
        요구사항 → 창 해석 경로
분리    Academic 과 KRX 의 가격 · 비용 · 수량 규칙 · 롱온리와 양방향의 전이 유효성
        profile 별 사실성 표시와 한계 · 소비자마다 무엇을 요구하나
```

### 2.10 제약이 어디에 속하나

**규칙 1 — 무엇과 함께 바뀌나.** 거래소와 함께 바뀌면 거래소, 계좌와 함께 바뀌면 계좌, 회계 항등식이면 공통
불변식이다.

| 사실 | 자리 |
|---|---|
| 분수 · 로트 · 수량 단위(academic `0.000001`, KRX `1`), 허용 방향, 가격 · 비용 · 체결 시각 | 거래소 (`domain/listing.py`, profile) |
| 음수 보유, 음수 현금 | 계좌 |
| `NAV = 현금 + Σ 보유 가치` | 공통 불변식 |

**규칙 2 — 속성은 무엇과 함께 바뀌나.** 거래소마다 다르면 거래소, 시간에 따라 다르면 데이터, 둘 다 아니면
종목이다: `kind`(주식/ETF) · 통화는 종목(`domain/instrument.py`), 수량 단위 · 허용 방향 · 비용은 거래소 규칙,
거래 가능 여부와 체결 가격은 체결표(시각마다), 섹터 분류와 유니버스 편입은 데이터다. **거래정지는 거래소가
판단한다** — 같은 종목이 KRX에선 정지이고 academic에선 거래 가능할 수 있다(`UC-ACADEMIC-001`).

## 3. 시간 — 시계 둘

### 3.1 무엇이 어느 시각의 authority인가

| 사실 | authority |
|---|---|
| 판단 시각 (일정 시계) | run의 `schedule` — 거래일 필터 + 하루 안의 규칙. preflight가 전개해서 얼린다 |
| 시장 시각 (시장 시계) | run 기간 안에서 체결표가 가진 `trade_at`의 집합 |
| 관측의 가시성 | `available_at` — 창은 `available_at <= 평가 시각` |
| 수락된 판단 시각 | 엔진. 현재 사건의 평가 시각을 도장 찍는다. 덮어쓸 수 없다 |
| 정확한 체결 목표 | `FillRule` — 판단 뒤 첫 시장 시각, `at` · `after` · `within`으로 좁힌다 |
| 실제 상태 | 계좌 (append · mark commit) |

### 3.2 Schedule — 선언은 규칙이고, 전개는 데이터가 답한다

```yaml
schedule:            # 0.15.0 까지의 이름은 agenda
  every: 1d          # 1d · 2d · 1w · 1M 은 날을 고르고 at 과 짝을 짓는다
  at: '09:00'        # 1m · 5m · 1h 는 from 과 to 사이의 시각을 고른다
  on: last           # 1w · 1M 을 주/월의 마지막 거래일에 (기본은 first)
  days_from: prices  # DataModel run 만: 거래일을 빌려 올 dataset (시장 시계가 없으므로)
```

- 선언(사람이 쓴다) → preflight가 **거래일 위에서 전개**(전략 run은 체결표에 행이 있는 날, DataModel run은
  `days_from` dataset의 날) → 시각 + 안정 id의 유한한 순서(`ScheduledEvent`) → identity 해시가 run에 각인된다.
  이후로는 얼린 사건 목록만 소비한다.
- **날짜는 유도해도 되고, 시각은 안 된다.** 1분 체결표든 일별 체결표든 거래일은 250개로 같다(밀도 무관). 시각을
  유도하면 1분 표가 97,500개를 만든다(밀도가 결과를 바꾼다). 별도의 거래일 달력 dataset은 만들지 않는다 —
  **체결표에 행이 있는 날이 거래일이다.**
- 사람이 사건 목록을 타이핑하지 않는다. cron · RRULE · 달력 추론을 거부한 이유는 규칙이 싫어서가 아니라 패키지가
  시장 사실을 추측하게 되기 때문이다. 거래일은 데이터가 답하고 하루 안은 산술이므로 어느 쪽도 추측이 아니다.
- 월말 cadence는 일정에 그 시각을 넣어서 표현한다(`every: 1M, on: last`). 전략이 미래 일정을 읽지 않고, 엔진이
  달력을 추론하지 않는다.

**일정 시계를 체결표에서 유도하지 않는 이유** (시도했고 기각됐다):

1. **장 마감 뒤 공시 데이터를 못 쓴다.** 일별 데이터는 D 19:00에 나오고 D+1 09:00부터 쓸 수 있다. 판단이
   시장 시각(15:30)에 돌면 볼 수 있는 최신이 D−1의 것이라 `D−1 데이터 → D 15:30 판단 → D+1 15:30 체결`로 한 칸이
   통째로 낭비된다. 독립 일정이면 `D−1 데이터 → D 09:00 판단 → D 15:30 체결`이다.
2. **격자를 공유하면 느린 전략이 비용을 문다.** 1분 체결표를 등록하면 월 1회 전략도 97,500번 불린다.

**어휘가 DES인 이유**: 이 루프는 사건 목록 전체를 미리 알고 시각 순서로 처리하는 이산 사건 시뮬레이션이다. DES의
표준 어휘는 event · future event list · clock이다. 0.15.0의 `agenda`는 SICP · DES에서 "시각순으로 섞인 할 일
대기열 전체"를 뜻하는데 여기선 판단 시각 목록 하나에 붙어 있었고, `occurrence`는 iCalendar의 말이었다. 둘 다
어휘에서 뺀다. 판단 시각은 **schedule이 만든 ScheduledEvent**, 체결 시각은 **체결표가 만든 MarketEvent**다.

### 3.3 두 시계의 병합과 한 시각의 순서

엔진은 정확히 두 정적 원천 — 얼린 `ScheduledEvent`들과 run 안의 체결표 시각들 — 을
`(시간대가 있는 시각, 시장이 먼저, 안정 id)` 키로 병합한다. **run 도중에는 사건을 만들지 않는다.** 그래서 같은
얼린 입력의 두 run은 같은 trace를 만든다.

```text
1. ACCRUE      지난 보유 기간이 번 것             → 원장    (자리만, §4.8)
2. EXECUTE     이 시각이 목표인 대기 의도의 체결   → 원장
3. VALUE       결과 장부를 이 시각의 가격으로 평가  → 계좌의 평가
4. OBSERVE     Compliance가 committed 계좌를 본다  → 증거
5. DECIDE      일정 시계가 이 시각에 걸렸으면       → 목표 포트폴리오   (별도 사건, 1-4 뒤)
```

- **ACCRUE가 EXECUTE 앞인 이유**: 배당 · 이자 · 대차 수익 · funding은 지난 보유 기간의 대가다. 이번 시각에 체결된
  것은 아직 그 기간을 보유하지 않았다.
- **DECIDE가 마지막인 이유**: 방금 평가된 장부를 봐야 한다. OBSERVE와 DECIDE 사이 순서는 정확성과 무관하지만(둘 다
  계좌를 바꾸지 않는다) 결정성을 위해 고정한다.
- **`체결 시각 > 판단 시각`은 언제나 성립한다.** 한 시각에서 체결되는 것은 그보다 이전의 판단이다. 판단과 체결이
  같은 시각인 구성은 허용하지 않는다.
- "데이터가 도착했다"는 사건이 아니다. 창의 술어(`available_at <= 평가 시각`)일 뿐이다.

### 3.4 FillRule — 언제 체결되나

```text
FillRule(trade_price, timezone, at=None, after=None, within=None)

기본     판단 시각보다 엄격히 늦은 첫 시장 시각
at       하루 중 그 현지 시각의 시장 시각만 후보로     1분 격자에서 종가 체결
after    판단 뒤 최소 경과                             지연 체결
within   최대 허용 간격. 넘으면 목표가 없다(실패)       "당일에 못 채우면 실패"
```

- 후보: `trade_at > 판단 시각` 이고 `trade_at <= end`인 시장 시각. `at`을 비우면 격자 전체가 후보이고, 1분
  체결표에서 판단 뒤 첫 점이 곧 다음 분이다 — **매 분 체결이 이렇게 표현된다.**
- `trade_price`는 run의 `execution:`이 고른다. 같은 체결표로 한 run은 종가에, 다른 run은 시가에 체결한다 — 표를 두
  번 등록하지 않는다. 선언한 가격 컬럼이 없거나 유한한 양수가 아니면 실패한다. 다른 컬럼으로 대체하지 않는다
  (`UC-FILL-001`).
- 목표가 없거나, 목표가 판단 시각 이하이거나, `end` 뒤이거나, 존재하는 `(trade_at, instrument)` 키가 중복이면
  그 콜백의 수락이 원자적으로 실패한다(§3.6). run 사이에 대기 의도를 넘기지 않는다.
- 요청한 종목의 행이 목표 스냅샷에 없으면 그 종목만 0주 체결(`absent`)이다.

### 3.5 평가는 매 시장 시각에

평가는 판단이 있든 없든, 체결이 있든 없든 **모든 시장 시각에서** 한다(0.2 시절의 결함 — 거래일에만 NAV가
움직이던 것 — 은 그래서 없어졌다). 일별 체결표는 거래일마다 NAV 한 점, 1분 체결표는 분마다 한 점을 만든다.
평가는 언제나 판단보다 조밀하거나 같다 — 이것은 손잡이가 아니라 정의다. 체결 권한이 없는 run(DataModel run)은
시장 시계가 없으므로 평가하지 않는다. 무엇으로 평가하는지는 §9.5.

### 3.6 콜백 수락은 원자적이다

`Rebalance` 하나는 한 경계 안에서 이 순서로 staging된다: ① 경제적 내용 검증 ② 엔진의 판단 시각 도장 ③
`FillRule` 목표 해석 ④ 목표의 인과 · 범위 · 시간대 · 출처 검증 ⑤ 모델 상태 · 판단 증거 · 최신 대기 의도 포인터를
함께 commit. 어느 단계든 실패하면 그 콜백의 새 쓰기는 전부 버려지고, 이전 대기 의도 · commit된 상태 · 불변
증거는 그대로다.

세 결과는 끝까지 구별된다.

| 결과 | 무슨 일 |
|---|---|
| `Hold` | 콜백 성공, 판단 없음. 모델 상태는 commit, **이미 있던 대기 의도는 건드리지 않는다.** 주문 없음, 체결 행도 필요 없다 |
| `Rebalance` 수락 | 판단 · 상태 · 최신 대기 의도가 원자적으로 commit. 새 의도가 이전 대기 의도를 대체한다(둘의 판단 trace는 남는다) |
| 체결 0주 | 판단도 주문도 있었지만 거래소가 채우지 않았다 — 이유가 붙는다(§8.5) |

- **warm-up은 모델의 `memory`가 돌려주는 평범한 `Hold`다.** 엔진은 run 시작의 사건을 세서 건너뛰지 않는다.
- 0.15.0 문서의 한 절(archive §5.5)은 `Hold`를 "현재와 같은 목표를 가진 완전한 의도, 델타 0 주문"이라고 적었지만 코드와
  나머지 절은 위와 같다. **이 문서는 코드를 따른다**: `Hold`는 아무것도 예약하지 않는다.
- 대기 의도의 목표가 이미 지나 있다면 늦은 체결이 아니라 깨진 불변식이다 — 목표는 루프가 걷는 같은 시계에서
  골랐다.
- run은 `end`까지 모든 시장 시각을 걷고 대기 의도가 비어 있을 때만 성공으로 끝난다.

### 3.7 빈도 독립

- 관측 빈도와 판단 빈도는 독립이다. 한 날에 판단이 0번, 한 번, 여러 번일 수 있다.
- 체결 · 평가 · 감시는 한 시계(시장 시계)를 공유하므로 서로 독립이 아니고, 일정 시계와는 독립이다.
- **체결표의 밀도를 바꿔도 얼린 판단 사건의 집합 · 시각 · 순서는 바뀌지 않는다.** 판단과 체결 trace는 같고, 평가와
  감시의 횟수만 시장 시각 수를 따른다.
- 별도의 거래소 달력 provider, cron/RRULE, live 타이머, 데이터 도착 콜백, 끼울 수 있는 사건 원천은 없다. 닫힌 시간
  모델이다. `UC-CALENDAR-001`은 은퇴했고 날짜 유도만 돌아왔다.
- MVP의 체결은 의도 하나에 정확한 스냅샷 하나다. 부분 체결 · child order · TWAP/VWAP은 미래 기능이다.

### 3.8 결정성

같은 얼린 일정과 구간, 같은 체결표, 완전한 얼린 입력은 같은 사건 · 상태 전이 · trace를 만든다. 캠페인의 모든
이동 단계는 이것을 관문으로 쓴다 — showcase의 기록 digest가 한 글자도 바뀌지 않아야 한다.

## 4. Component — 추상화 하나, 역할 넷, 자리 하나

### 4.1 무엇인가

**Component는 엔진이 어떤 사건에 그 사건의 시각과 함께 불러 주는 객체다.** DataModel, StrategyModel,
Exchange, Compliance는 모두 Component이고, 넷이 공유하는 것은 넷이다.

```text
읽을 것을 선언한다        inputs()        별칭 → DatasetInput.  아무것도 안 읽어도 된다
그 시각의 창을 받는다      Call            그 사건에서 닿을 수 있는 것 전부, 그 이상은 없다
기억을 들고 다닌다        memory          엄격한 JSON.  콜백 전에 복원되고 콜백과 함께 commit 된다
판단 하나를 돌려준다      콜백의 반환값    행 · 결정 · 체결 · 발견
```

역할이 서로 다른 것은 **둘뿐이다 — 언제 불리는가, 답을 누가 받는가.** 받는 것과 주는 것은 그 둘에서 따라
나온다. 그리고 그 둘은 base 클래스가 아니라 **배선표**가 정한다.

**왜**: 역할마다 선언 방식이 달랐을 때 처음 온 사용자가 두 역할의 차이를 열 줄짜리 표로 만들어야 했다.
오너 판정: *"현재 차이의 크기 자체가 결함이다."* 없으면 역할마다 읽기 선언 · 기억 · 검증이 따로 자라고, 한
역할에서 고친 것이 다른 역할에서 다시 틀린다.

### 4.2 배선표 — 이것이 아키텍처다

```text
역할            시계          받는 것                              답을 받는 곳
────────────────────────────────────────────────────────────────────────────────
DataModel       일정 시계     창                                  창고 (warehouse)
StrategyModel   일정 시계     창 + 계좌 + 이력                    거래소 (exchange)   ← 목표 포트폴리오
Accrual         시장 시계     보유 + 창                            원장 (ledger)       (자리만, §4.8)
Exchange        시장 시계     주문 + 시장 상태 + 계좌 + 종목 사전   원장 (ledger)
Compliance      시장 시계     창 + committed 계좌                  증거 (evidence)
```

코드에서는 `domain/wiring.py`의 `WIRING`(데이터)이고, 시장 시각의 순서는 같은 파일의
`MARKET_CLOCK_ORDER = (ACCRUAL, EXCHANGE, COMPLIANCE)`다. 역할의 이름은 **`Role` 하나**다 — 0.15.0에 있던
두 번째 열거(`extension/component.py::ComponentKind`)는 이것으로 합친다.

**이 표는 프레임워크의 것이고 닫혀 있다.** 역할을 하나 더 만들려면 행을 하나 더 만들어야 하고, 행은 시계와
수신자를 정하는 일이라 프레임워크의 결정이다. 테스트(`tests/domain/test_the_wiring_table.py`)가 행 없는
역할과 표와 어긋나는 역할 클래스를 거절한다.

### 4.3 부품(Part)과 도구(Tool)

기준은 하나 — **자기 시계를 선언하는가.**

```text
Part   시계를 선언한다.  run 하나에 정확히 하나      DataModel · StrategyModel
Tool   시계가 없다.  남의 시계(시장 시계)에 붙는다    Exchange · Compliance · (Accrual)
```

부품 = 도구 + 시계. run의 `schedule`(§3)이 곧 그 run의 부품이 불리는 시계다.

### 4.4 Call — 한 사건에서 닿을 수 있는 것

```text
Call                  at                                  모든 역할: 이 사건의 시각
├── DataCall          + read · rows                        선언한 읽기
├── StrategyCall      + read · rows · account · history · event_id
├── ComplianceCall    + read · rows · account(committed · 평가됨) · instruments
└── ExecutionCall     + orders · account · snapshot · instruments · rules
```

- `read(alias, field)`는 panel grain 별칭을, `rows(alias)`는 긴 표 별칭을 읽는다. 세 역할이 같은 동사를 쓰고,
  엔진 쪽의 구현도 하나다(`run/engine/calls.py`).
- 계약(추상 클래스)은 `component/`에 있고 저자는 받기만 한다. 구현은 엔진이 한다 — 포트는 안쪽, 어댑터는
  엔진 쪽.
- `event_id`는 이 판단이 몇 번째 일정 사건인지를 말한다. memory에 넣어 cadence("5번에 한 번")를 센다.
- 0.15.0에서 세 Call은 ABC였고 `ExecutionCall`만 거래소 모듈의 dataclass였다. 공통 base가 없어서 "모든
  컴포넌트는 Call을 받는다"가 타입으로 존재하지 않았다.

**왜 bounded인가**: Call이 곧 그 콜백의 권한 전부다(least authority). 전략이 체결표를 직접 열 수 있으면 체결
시각의 가격을 판단에 쓸 수 있고, 그것이 look-ahead다. 없는 경로는 쓸 수 없다.

### 4.5 반환값

| 역할 | 콜백 | 돌려주는 것 | 모듈 |
|---|---|---|---|
| DataModel | `compute(call)` | `Rows` — 종목마다 dict 하나. `available_at`은 프레임워크가 찍는다 | `component/datamodel.py`, `domain/rows.py` |
| StrategyModel | `decide(call)` | `Hold` 또는 `Rebalance` — 완전한 목표 포트폴리오 하나 | `component/strategy/decision.py` |
| Exchange | `execute(call)` | `FillBatch` — 체결 또는 0주 체결과 그 이유 | `domain/fill.py` |
| Compliance | `observe(call)` | `ComplianceFinding` — 무엇을 쟀고 한도가 얼마였나 | `component/compliance/base.py` |

반환값은 전부 엄격하고 얼린 값이다. 틀린 모양은 저자가 볼 수 있는 경계에서 거절되고, 엔진 몇 층 안쪽에서
터지지 않는다. 결정에 붙는 나머지 — 의도 id, 전략 id, 무엇을 읽었나, 어느 계좌 버전을 봤나 — 는 엔진이
찍는다. 콜백이 그것을 적으면 갖지 않은 권한을 주장하는 것이다.

### 4.6 base와 구현은 다른 파일이다

```text
component/
├── base.py                    Component · Part · Tool · Call
├── datamodel.py               DataModel · DataCall
├── strategy/     base.py      StrategyModel · StrategyCall
│                 decision.py  Hold · Rebalance
│                 history.py   AccountHistory · AccountHistoryInput
│                 recorder.py  TableSpec · InvocationRecorder
├── exchange/     base.py      Exchange · ExecutionCall · 모든 profile이 쓰는 요청 검사
│                 academic.py  AcademicExchange — 마찰 없는 학술용
│                 krx.py       KrxExchange — KRX 규칙의 선언된 부분집합
└── compliance/   base.py      Compliance · ComplianceCall · ComplianceFinding
                  report.py    StampedFinding · ComplianceReport — 프레임워크의 판정(허용오차)
                  shipped.py   출하 규칙을 이름으로 찾기
                  no_short.py · single_name_cap.py  — 출하하는 규칙
```

- **출하하는 구현도 사용자의 것과 같은 문으로 들어온다.** `academic`, `krx`, `no_short`, `single_name_cap`은
  특별 대우를 받지 않는다 — 등록되고, 지문이 찍히고, 규격 검사를 받는다.
- **Exchange는 profile을 상속해서 쓴다.** 사용자는 출하된 profile(`AcademicExchange`, `KrxExchange`)을
  상속해 상장 종목과 비용을 더할 수 있지만, `execute`를 바꾸는 서브클래스는 싣기(load)에서 거절된다. profile의
  사실성 주장이 곧 그 체결 규칙이기 때문이다(§8).
- 0.15.0에서는 `Exchange`의 base와 `AcademicExchange` 구현이 `exchange/venue.py` 한 파일에 있었고, 구현 셋이
  세 곳(`venue.py`, `venues/krx.py`, `agent/sample/`)에 흩어져 있었다.

### 4.7 등록된 컴포넌트를 싣는 법

```text
component/reference.py     ComponentRef — 경로 · 객체 이름 · 역할 · 지문.  얼린 참조
component/fingerprint.py   소스 파일의 지문
component/conformance.py   실제로 import 해서 약속한 메서드가 맞는 시그니처로 있는가.  쓰지 않는다
component/loading.py       등록된 코드를 import 해 엔진이 부를 인스턴스로.  id 대조
component/scaffold.py      `vqapr new` 가 내는 템플릿 — 쓴 그대로 돈다
```

**규격은 등록 때 검사한다**: 메서드 이름이나 파라미터가 틀린 컴포넌트는 등록에서 이름을 대며 거절된다.
없으면 등록은 깨끗이 되고 run 한가운데에서 실패하고, 그때의 오류는 원인에서 멀다.

Compliance 규칙은 자기 id(`compliance_id`)를 한 번 선언하고, 싣기가 그것을 등록된 id와 대조한다. 두 이름이
다르면 run이 시작하기 전에 거절된다.

### 4.8 Accrual — 자리만

배당 · 쿠폰 · 이자 · 대차 수익 · perpetual funding · 선물 일일 정산 · 펀드 설정/환매가 갈 자리다. 배선표에
행이 있고(시장 시계 첫 단계, 보유 + 창을 받고, 답은 원장), 엔진의 `accrue` 단계는 있지만 **아무것도 하지 않는다.**

**왜 자리만인가**: 배당락일에 인식하나 지급일에 인식하나, 원천징수는 얼마인가, 재투자하나 — 전부 경제적
선택이고 프레임워크가 정하면 안 된다. 첫 구현이 생길 때 `component/accrual/`(`base.py`와 구현들)이 되고, 답은
원장 항목 한 줄(`LedgerEntry`, origin `dividend` 등)이다(§9). **계좌 코드는 한 줄도 바뀌지 않는다.** 구현이
없는데 폴더를 먼저 만들지 않는다 — 없는 확장점을 있는 것처럼 보이게 하기 때문이다.

### 4.9 Constraint는 역할이 아니다 — 짓는 것은 전략, 보는 것은 Compliance

"단일 종목 5% 한도"에는 두 얼굴이 있고, 둘은 다른 시계에 산다.

```text
짓기   전략이 목표 포트폴리오를 만들 때 상자 안에서 만든다      일정 시계    portfolio/bounds.py (함수)
보기   체결된 계좌가 한도 안에 있는지 매 시장 시각에 잰다       시장 시계    component/compliance/ (역할)
```

- **짓기는 최선이고, 최선은 재량이며, 재량은 전략의 것이다.** 프레임워크가 보장할 것이 없으므로 확장점이 아니라
  함수 모음이다: `lo, hi = intersect(no_short(names), single_name_cap(names, benchmark, cap))` 다음
  `optimize(desired, lower=lo, upper=hi, ...)`.
- **보기는 사실 관찰이고, 프레임워크가 보장한다.** 그래서 역할이다. 규칙은 **자기 파라미터**로 잰다 — 전략이
  쓴 상자를 물려받지 않는다. 감시자가 감시 대상의 목표를 물려받으면 자기 채점이다. 둘이 다르게 나오면 그것이
  정보이고, 리포트가 나란히 둔다(오너 결정).
- 위반은 run을 멈추지 않는다. 기록된다 — 어느 규칙이, 한도가 얼마였고, 무엇을 쟀고, 누가 넘었나 —
  `vqapr.monitoring` 표에 규칙마다 시각마다 한 행.
- 허용오차는 규칙마다가 아니라 **프레임워크가 한 번** 판정한다(기본 `max(한도의 1%, NAV의 10bp)`). 1주 단위로
  체결되고 체결 뒤에 평가되므로 실현 비중은 목표에서 조금 벗어나고, 허용오차가 없으면 그 잔차가 진짜 위반과
  같은 칸에 들어간다. 저자의 `passed`와 프레임워크의 `verdict`(`held` / `within_tolerance` / `breached`)를
  나란히 기록한다.

### 5.1 종목 — 거래소와 무관한 정체

- `kind`(stock · etf · index · factor)와 통화는 시간에 따라서도, 거래소에 따라서도 바뀌지 않으므로 종목에 둔다.
  그래서 비용이 **종목 id가 아니라 종류**를 가리킬 수 있다 — KRX는 ETF에 매도세를 물리지 않고, 그것은 종목 목록이
  아니라 종류에 관한 규칙이다.
- 종목에는 `exchange_id`도, 거래 가능 여부도 없다. 같은 종목이 거래소마다 수량 단위가 다르고, 거래 가능 여부는
  체결표가 시각마다 답한다.
- 하위 타입은 그 종류가 자기 필드를 얻을 때만 만든다(선물: 만기 · 승수, 채권: 만기 · 쿠폰).
- **종목 사전(`InstrumentRoster`)은 통째로 읽는다.** 시간축이 없으므로 PIT 창으로 읽지 않는다 — 창고에 넣으면
  "이 종목이 언제부터 ETF였나" 같은 없는 질문이 생긴다. run은 `instruments:`로 등록된 사전을 가리키고, 엔진이
  사전 전체를 `ExecutionCall.instruments`로 거래소에 건넨다.
- **세 집합은 독립이다.** 체결표 3,000종목, 선언 200종목, 주문 30종목. 요구하는 포함관계는 둘뿐이다: 주문 ⊆ 선언
  (거래소가 세금 · 승수를 정하려면 정체를 알아야 한다), 주문 ⊆ 체결표(가격을 알아야 체결한다).
- 검사는 두 시점으로 갈린다. preflight는 선언이 하나라도 있는지만 본다(없으면 `roster.absent`, 412). 선언되지 않은
  종목에 대한 주문은 run 중에 **전부 모아서** `instrument.undeclared`로 run을 실패시킨다 — 경제적 사실이 아니라 설정
  오류이므로 0주 체결로 넘기지 않는다.

### 5.2 목표 포트폴리오 — intent

- `PortfolioIntent`는 전략이 돌려주는 **경제적 내용**만 담는다: 목표(`PortfolioTarget` — 종목과 **비중**),
  `cash_target`, `Budget`, 무엇을 읽었나(`source_refs`), 본 계좌 버전, 모델 상태 참조.
- 두 단계가 있다. **제안된 의도**(전략의 것: 내용 + 출처, 시각 없음)와 **수락된 의도**(엔진의 것: 내용 + 도장 찍힌
  판단 시각 + 해석된 체결 목표). 대기 포인터가 가리키는 것은 두 번째다.
- **목표는 비중뿐이다.** 수량을 선언할 수 없다. 콜백은 체결 가격도 NAV도 보지 못하므로 수량은 이미 틀린 가격으로
  계산된 것이 되고, `cash_target`까지 정확히 맞추기를 강요한다. 수량 변환은 체결 시각에 `plan_orders`에서 한 번만
  일어난다(§8.3).
- `cash_target`은 `1 − Σw`로 유도하지 않는다. 구성이 정한 값이다(§7.5).
- **`Budget`은 intent의 필드다** — 방향(롱온리 · 양방향), 현금 비중의 허용 범위, 종목 비중의 허용 범위. 목표 비중과
  함께 이동하고 수락 단계와 `plan_orders`가 다시 검사한다. 한 개념이 소유하는 value object이므로 같은 모듈에 산다.
- **만들 때 검사한다**: `Σw + cash_target = 1`, `cash_lower <= cash <= cash_upper`, 종목 유일, 유한한 값, 방향과
  profile의 호환. 계산한 쪽(solver의 표류, 손으로 만든 목표, 버그)을 믿지 않는다. **종목별 상한은 만들 때 검사하지
  않는다** — 상자는 전략의 재량이고, 지켜졌는지는 Compliance가 체결된 계좌에서 본다(§4.9).
- 분수 · 로트는 intent에서 검사하지 않는다. 거래소가 안다.

### 5.3 거래소가 한 종목을 거래하는 규칙 — listing

- `TradeRule`이 거래소의 한 종목에 대한 권한 전부다: 수량 단위, 최소 수량, 분수 허용, 허용 방향, **매수 · 매도 각각의
  비용**(`SideCost`). 수량과 비용은 한 규칙이다 — 둘 다 "이 거래소는 이 종목을 어떻게 하나"에 같은 속도로 답한다.
- 종류별 조건(`TradeTerms`)을 두면 거래소가 종류에 따라 청구한다. 종류는 거래소의 사본이 아니라 **등록된 종목
  사전**에서 온다 — 거래소가 자기 사본을 들면 체결이 기록한 종류와 청구한 비용이 어긋날 수 있다.
- `ExchangeRulesView`는 계획과 체결이 읽는 닫힌 투영이고, 종목 사전에 묶인다. 다른 사전에 묶인 view는 거절한다.
- 비율은 거래소 설정의 상수다. 같은 거래소 클래스를 다른 비율로 두 번 등록하면 지문이 다른 두 거래소가 된다 —
  비율이 바뀐 기간은 다른 run이다(§16).

## 6. data — 그 시점까지만 읽기

### 6.1 세 사람

데이터 층에는 세 독자가 있고, 한 사람의 개념이 다른 사람에게 새는 것이 가장 흔한 설계 오류다.

```text
준비하는 사람   xlsx · csv · DB → parquet + 선언.  패키지 밖의 일 (사용자와 그 에이전트)
등록하는 사람   경로 · 파티션 · 물리 컬럼 이름.  패키지가 검증하는 선언
소비하는 사람   dataset_id · 프레임워크 필드 이름 · lookback.  그 밖에는 아무것도 모른다
```

패키지는 형식 변환도 스키마 추론도 하지 않는다. 완성된 parquet과 선언을 받아 계약이 성립하는지 판정한다
(PRD §4.0). 등록 가능한 dataset의 계약은 기계가 읽을 수 있게 공개한다.

### 6.2 등록 — 두 층

```text
물리    SourceSpec          어디에 어떻게 쌓여 있나: 경로 · hive 파티션 여부 · 필드 파티션    data/source.py
의미    DatasetRegistration 무엇을 뜻하나: dataset_id · source · instrument_field ·           data/dataset.py
                            available_at(컬럼 이름) · key_fields · fields · grain
```

- **`available_at`은 규칙이 아니라 컬럼이다.** 패키지는 그 뒤의 가정을 묻지도 평가하지도 기록하지도 않는다.
  검사하는 것은 시간대가 있고, 비어 있지 않고, 논리 키와 함께 유일하다는 것뿐이다.
- **grain은 선언이다** — `instrument_instant`(시각 × 종목마다 값 하나, panel을 만들 수 있다), `instant`(시각마다
  하나, 종목축 없음 — 지수 레벨 · 금리 · 환율), `rows`(벤더의 긴 표, 저자의 `key_fields`로 유일). grain 없는 등록은
  세 값을 말하며 거절된다.
- `fields`는 프레임워크 이름 → 물리 위치다. **이름 바꾸기는 허용하고 역할 붙이기는 금지한다**(`"당일시가(원)"` →
  `open`은 되고, `→ execution_price`는 안 된다). 필드 값은 식(expression)이고 문장(`FROM` · `GROUP BY` ·
  서브쿼리)은 거절한다 — 등록에 숨은 두 번째 ETL이 생기지 않게.
- 넓은 표와 필드 폴더(`item=BPS/`)는 등록만 다르고 소비자 선언은 같다. 필드 폴더가 필요한 기준: 필드들이 서로 다른
  시각에 알려지거나, 서로 다른 키 축을 가질 때. 망설여지면 넓은 표 — 소비자가 볼 수 없으므로 되돌릴 수 있다.
  `year=2024/` 같은 파티션은 가지치기용일 뿐 결과를 바꾸지 않는다. 식별자로 파티션하지 않는다.
- **패키지는 등록된 값이 PIT 안전한지 판정하지 않는다**(ETL에서 계산한 중심 이동평균 같은 것). 막을 자리가 없고,
  반쪽짜리 보장은 없는 것보다 나쁘다. vqapr이 보장하는 것은 **선언한** 가용 시각을 지키는 것이다(PRD §3.2).
  피해야 할 look-ahead 패턴은 등록 전 인터뷰에서 skill이 묻는다.

### 6.3 한 문 — 한 번 재고, 이후엔 지문

`data/verification.py`가 물리 읽기의 유일한 문이다.

```text
verify_source(registration, spec)    등록 때 한 번:  컬럼과 타입 → 키 (grain 대로) → 기간 → 값 → 체결 가격 → 지문
require_verified(registration, spec) 이후 모든 읽기: 잰 적이 있나, 지금 파일의 지문이 그때와 같은가.  스캔 없음
verify_roster(...)                   종목 사전
```

- 등록에는 두 반쪽이 있다: 사람이 **선언한** 반쪽(컬럼 · 키 · 단위)과 문이 **잰** 반쪽(기간 · 지문 · 체결 가능한
  가격 컬럼). **dataset의 identity는 선언이고, 지문은 검증에 쓰는 잰 사실이다.**
- 등록 뒤 파일이 바뀌면(행을 덧붙인 것도) 읽는 쪽이 지문 하나로 알아채고 `dataset.source_changed`로 거절하며, 고치는
  법을 말한다: 같은 선언으로 다시 등록하라. 재등록은 선언한 반쪽이 같으면 잰 반쪽만 갈아 끼운다.
- `data/scan.py`가 `SourceSpec`을 여는 유일한 코드이고, 의미를 모른다. 스캔이 없으면 키 유일성 검사가 lookback 없는
  전체 읽기를 요구하게 되고, 그 구멍이 곧 look-ahead 경로다.

### 6.4 요구사항과 lookback — 소비자가 선언한다

- 소비자는 `inputs()`에 별칭마다 `DatasetInput`을 적고, 엔진이 필드마다 `DataRequirement`로 번역한다.
- **lookback은 저장소 질의까지 내려간다.** 다 읽고 자르지 않는다(`UC-LOOKBACK-001`).
- **모든 lookback은 과거를 향한다. 미래 방향 타입이 없다** — 그래서 어떤 소비자도 미래 관측을 끌어올 수 없다.
  미래가 필요해 보이는 계산(라벨)은 늦은 시각에 값을 기록하고 소비자가 시간으로 맞춘다.

| lookback | 뜻 | grain |
|---|---|---|
| `RowsLookback(n)` | pivot된 표의 마지막 n행 — 모든 종목에 같은 시각들 | panel grain (`instrument_instant` · `instant`) |
| `InstantsLookback(n)` | 종목 · 필드마다 비어 있지 않은 마지막 n개 관측 | `rows`만 |
| `CalendarLookback` | 달력 하한 하나. 모든 종목에 같은 창 | 모두 |

바꿔 쓰면 preflight와 읽기가 이름을 대며 거절한다 — 타입이 방향을 잡는다. "이번 달만" 같은 경계를 lookback에
더하지 않는다. 넓게 받고 소비자가 거른다(`available_at` 상한은 그대로라 PIT는 안전하다).

- **계산된 결과도 같은 `DataRequirement`로 읽는다.** `ArtifactRequirement`는 없다 — PIT 경로가 둘이면 파생 데이터에서만
  look-ahead가 생긴다. 계산 사슬이 얼마나 깊어도 개념이 늘지 않는다.

### 6.5 창과 panel — 창은 사각형 하나다

- 창(`ModelWindow`, `data/window.py`)은 **선언한 종목 × 선언한 lookback**의 사각형 하나이고, `available_at <= 평가
  시각`으로 잘린다. 1 × N 단면, 20 × N 이동평균, 1,260 × N 5년 베타가 같은 모양이고 비율만 다르다. 식 DSL은 없다 —
  사각형 전체를 건넨다.
- **Panel은 run당 한 번 만든다** — (dataset, 선언한 필드, 종목)마다 run의 기간 + lookback만큼 한 번 스캔해서, 필드마다
  `(시각 × 종목)` 숫자 행렬 하나로. 이후의 모든 창은 그 행렬의 **복사 없는 조각**(`PanelWindow`)이다. 한 시각의
  행이 `CrossSection`(종목 → 값), 한 종목의 열이 `Series`(시각 → 값)이고, `matrix()`는 numpy view를 준다.
- panel grain이 아닌 긴 표는 `Observation` 행으로 읽는다(`call.rows(alias)`).
- 창은 실제로 읽은 것을 기록해 lineage를 만든다. 읽지 않은 dataset은 의존이 아니다.

### 6.6 저장소와 cube

- 저장소(`data/store.py`)는 run의 기간(horizon)을 알고 모든 읽기를 그 범위로 자른다. 3년 표에서 3주만 읽는다.
  기간 경계는 SQL 문장에 TIMESTAMPTZ 리터럴로 들어간다(파라미터 바인딩은 프로세스의 첫 문장에서 수백 ms를 낸다).
- `--jobs` 배치는 dataset마다 cube(`data/cube.py`)를 한 번 굽는다 — 숫자 필드마다 `(시각 × 전 종목)` float64
  행렬을 `.npy`로. worker는 원천 지문이 같은지 확인한 뒤 메모리 매핑으로 자기 기간을 잘라 쓴다. 배치가 끝나면 지운다.

### 6.7 체결표 — 데이터이고, run이 가격을 고른다

- 체결표는 **등록된 dataset**이고 체결 역할을 갖는다 — 어느 필드가 거래 가능 여부인가. 필수 모양: `trade_at`(시간대),
  `instrument`, `is_tradable`(방향 구분 없는 불리언 하나), 가격 컬럼 하나 이상. 거래 가능 여부는 식으로 유도할 수
  있다(정지 이력이 없으면 `"거래대금" > 0`). 그 규칙은 선언에 얼린다.
- **체결표에는 `available_at`이 없다.** 관찰자가 없다 — 15:30의 가격은 늦게 알려지는 관측이 아니라 거래소의 상태다.

| | 관측 dataset | 체결표 |
|---|---|---|
| 술어 | `available_at <= 평가 시각` (범위) | `trade_at = 체결 시각` (등호) |
| 모양 | 창, 많은 행, lookback 필수 | 점, 종목마다 정확히 한 행, lookback 없음 |
| 누가 읽나 | 선언한 누구나 | 엔진의 체결 · 평가 단계만 |

- 모델에게는 체결표로 가는 경로가 없다. 일별 판단에 분 단위 체결을 표현할 수 있어야 하고, 전략이 아침에 오늘의
  거래정지를 알면 안 된다. **전략 쪽의 거래 가능 여부**가 필요하면 `available_at`이 있는 별도 dataset을 구독한다.
  둘이 어긋나는 것이 "전략이 틀렸다"를 표현하는 방법이고, 둘은 합치지 않는다.
- 조회는 집합 단위 한 번이다: `trade_at = t AND instrument IN (목표 ∪ 보유)`. 종목별 조회로는 "행이 없다"와 "있지만
  false"를 가를 수 없다.
- **거래 불가 ≠ 평가 불가.** 가격 190에 `is_tradable = false`면 0주 체결, 평가는 190. 행이 없으면 0주 체결, 이전
  평가를 이어 든다(§9.5). 불변식 `is_tradable = true ⟹ 가격 > 0`은 한 방향이다 — 정지 종목도 가격을 가질 수 있다.
- 행이 없는 것을 조용히 건너뛰지 않는다. 사용자가 이 표를 거래소의 완전한 상태라고 선언했기 때문이다(가격 공백에서
  정지를 추측하는 qlib과 다르다).
- 체결표의 시각들이 곧 시장 시계다. 체결표는 거래일을 답하되 판단의 시각을 만들지 않는다(§3.2).

### 6.8 `available_at`은 패키지가 붙인다

- DataModel 출력의 `available_at = max(그 계산의 평가 시각, 창 안에서 실제로 읽은 available_at의 최댓값)`. 생산자는
  주장할 수 없고 위조할 수 없다. 3월 공시를 쓴 6월 말 계산은 6월 말부터 알 수 있다.
- 전 기간을 한 창으로 읽으면 모든 출력 행이 마지막 날부터 유효해져 과거 판단에 쓸모가 없어진다 — 금지 규칙 없이도
  스스로 무의미해진다.
- 전략이 발행하는 비중의 `available_at`은 그 판단의 사건 시각이다.

### 6.9 소비자가 아는 것과 모르는 것

소비자의 어휘는 `dataset_id` · `fields` · `lookback` · `coverage`뿐이다. 경로 · 파일 형식 · 물리 컬럼 이름 · SQL ·
넓은 표냐 폴더냐 · 원천이냐 계산이냐 · 저장소 백엔드는 소비자 API에 없다(`UC-DATA-003`). **감사 가능 ≠ 보임**:
얼린 입력은 경로 · 파티션 · 유도 규칙 · 저장소 선택을 전부 기록하지만, 소비자에게는 아무것도 건네지 않는다.
원천 dataset과 계산된 dataset은 소비자에게 구별되지 않는다.

## 7. 판단 — 전략, 신호, 포트폴리오

### 7.1 StrategyModel

- `decide(call) -> Hold | Rebalance`. 하나의 현재 사건에서 경제적 내용 하나를 돌려준다.
- `StrategyCall`이 주는 것: 선언한 읽기의 창, 현재 사건(`event_id`, 시각), committed 계좌(읽기 전용 스냅샷),
  선언한 계좌 이력. 주지 않는 것: 미래 일정, 저장소, 거래소, 체결표, 바꿀 수 있는 계좌.
- 기록은 `self.recorder`로 한다(§11.2). 기록은 읽을 수 없고 memory도 intent도 아니다.
- **수락된 의도는 반드시 체결 생명주기에 들어간다.** 건너뛸 수 없다. 비용이 걱정이면 profile을 바꾼다 — academic은
  비용 0 · 전량 체결이지만 체결 · 계좌 commit · 피드백은 똑같이 일어난다.

### 7.2 모델 상태 — memory와 payload

StrategyModel과 DataModel에 똑같이 적용되고, 저장 · 복원 코드는 한 곳에 있다.

- `memory`: 엄격한 JSON(`bool | int | float | str | list | dict | None`). 진행 위치 · 최근 시각 · 작은 계수처럼 사람이
  볼 수 있는 것. 비유한 수와 문자열이 아닌 키는 거절하고, 분리된 깊은 사본을 만든다 — 나중에 제자리에서 바꿔도 과거
  스냅샷이 변하지 않는다.
- `payload`: JSON에 맞지 않는 사적 상태(신경망 가중치). `save_payload()` / `load_payload()`로 모델이 저장 · 복원하고,
  프레임워크는 내용을 해석하지 않는다. 기본 hook은 아무것도 하지 않고, 빈 원천을 받아들여야 한다.
- **재시작 동등성**: 다음 호출에 영향을 주는 바뀌는 속성은 전부 memory나 payload 안에 있어야 한다. 숨은 영구
  상태(`self.counter`)는 금지다. 모델을 새로 만들고 commit된 상태를 복원하면 같은 결과가 나와야 한다. 전략
  파라미터(`n`, `threshold`)는 바뀌지 않는 설정이지 상태가 아니다.
- 엔진이 성공한 호출 뒤에 스냅샷을 찍는다 — 체결 여부와 무관하게(`UC-STATE-001`). 모델은 자기 상태를 commit하지 못한다.
- `initial_model_memory`가 없으면 새 모델이고 첫 콜백의 memory는 `{}`다. 이전 상태를 자동으로 찾지 않는다.
- 긴 계산은 `checkpoint()`로 작업 상태를 남기고, 같은 얼린 작업만 그것을 이어받는다. 작업 checkpoint는 추론 입력이나
  하류 입력으로 해석되지 않는다. 실패하면 이전 commit 상태가 남는다.
- 상태를 쓰는 DataModel은 얼린 평가 시각 순서로 불려야 하고, 병렬 · 부분 재생성이 불가능하다는 것이 출력에 기록된다.
  상태 없는 DataModel은 순서와 무관하다.

### 7.3 `Rebalance`와 `Hold`

- `Rebalance`는 완전한 목표 포트폴리오 하나다: 비중 · 현금 · 그것이 지켜야 할 `Budget`. `Rebalance.of(long=…,
  short=…, invested=…)`는 흔한 두 예산(롱온리, 양방향)을 만들고, `Rebalance.signed(weights)`는 부호가 방향이다.
  잘못 부르는 모든 방법이 여기서 종목 이름을 인용하며 거절된다.
- 포지션을 다 비우는 것은 `Hold`가 아니라 빈 `Rebalance`(현금 100%)다. `Hold`는 "아무것도 하지 마라"이므로 포지션이
  남는다.

### 7.4 사슬 — 전략 위의 전략

- 한 콜백 밖에는 사슬이 있다. 전략 B가 A의 저장된 결과를 `DataRequirement`로 읽고, C가 B의 것을 읽는다. 저장된
  결과는 dataset이다(비중, 그리고 성과 시계열).
- **run마다 자기 계좌가 있다.** C는 B의 결과를 읽지 B의 계좌를 읽지 않는다. lineage는 A의 배분이 A의 계좌에서
  만들어졌음을 보여야 한다(`UC-ALPHA-PATH-001`).
- 롱숏을 한 콜백 안에서 롱온리로 바꾸지 않는다 — 부호 있는 alpha가 덮이지 않고, 벤치마크나 강도를 바꿔도 앞 단계를
  다시 돌리지 않는다(PRD §2.1). enhanced index가 이 모양이다(§14.4).
- **run 안에서 다른 run을 돌리지 않는다.** 중첩 시계는 엔진의 시간 소유를 깨고, 재귀에 한계가 없고, 비용이 곱해진다
  (250 판단 × 후보 3 × 250일 = 187,500 대 750). 파라미터 선택은 바깥 루프로 한다: 후보마다 run → 비교 시각마다
  "지금까지 최선"을 표시하는 DataModel run → 그것을 읽는 메타 전략. 경로 의존 후보는 근사임을 결과에 적는다.
- 주문 분할이 필요해지면 nautilus의 별도 `ExecAlgorithm`처럼 한 시계 안의 부품으로 한다. 중첩 executor는 아니다.

### 7.5 `signals/`와 `portfolio/` — 저자가 부르는 순수 함수

둘 다 순수 함수 leaf다: 인자로만 받고, 데이터 · 계좌 · 시계를 모른다. 시가총액 같은 것도 인자로 온다 — 그렇지
않으면 데이터가 선언한 요구사항을 우회해 lineage에서 빠진다.

**`signals/`** — 값을 값으로.

- `transform.py`: 동점을 다루는 Decimal 순위, Fama-French 기준 시장 breakpoint(동일 개수 분위와 헷갈리지 않게
  이름을 붙였다), 노출 제거(`neutralize` — 사용자가 고쳐 쓸 원본, `UC-EXTENSION-001`).
- `evaluation.py`: IC · rank IC · 적중률 · decay. run이 이미 기록한 값으로만 잰다.
- 내장 함수는 구현이 어렵거나 방법론을 틀리기 쉬운 곳에만 둔다(PRD §2.7). demean · zscore · winsorize · rolling은
  pandas/numpy나 산술로 쓴다.

**`portfolio/`** — 신호를 목표 비중으로.

- `weights.py`: **부호는 언제나 신호에서 오고 크기만 다르다.** `signal_weight`는 |신호|에 비례, `proportional_weight`는
  신호 × 크기 panel에 비례, `equal_weight`는 균등. 셋 다 gross 1로 정규화한다 — 예산이 아니라 단위다. 예산은
  `rescale(weights, long=, short=, grid=)`가 롱과 숏을 따로 맞춘다. `grid`가 있으면 먼저 격자에 올리고 나중에 맞춘다.
  비어 있는 선택은 실패가 아니라 빈 비중이다. 결측 이름을 버리고 재정규화하지 않는다 — 실패한다.
- `optimize.py`: 상하한 · 거래정지 · 비용 아래서 잘라 내고 재분배하는 대신 **한 번에 푼다.** 선언된 목적은
  `min ||Lw − x^desired||² + Σ cost_i |w_i − w0_i| + λ||w − w0||₁`, 제약은 `Σw + c = 1`, `l <= w <= u`,
  `c_lo <= c <= c_hi`, `w_j = w0_j (j ∈ frozen)`. 구현은 선언의 부분집합이고 선언을 줄이지 않는다 — 비용 없는
  부분은 예산 초평면으로의 box projection이라 2n개의 breakpoint를 정렬해 승수를 **유리수로 정확히** 푼다. 반복도
  solver 패키지도 없다.
  - 현금 `c`는 유도값이 아니라 결정 변수다 — 잘린 비중이 "갈 곳"이 현금이다.
  - 거래할 수 없는 종목은 제외가 아니라 `w_j = w0_j`다. 조용한 제외는 PRD §10.2 위반이다.
  - `L`(look-through 행렬)은 목적에만 들어가고 제약에는 들어가지 않는다. 제약은 물리적 `w`에만 걸린다 — 계좌는 물리
    보유를 들고 Compliance도 그것을 잰다. `L`은 전략이 구성 종목 데이터로 만든다. 패키지 helper는 없다(PRD §8.2).
  - 수의 격자: `optimize()`를 드나드는 모든 비중은 표준 격자(`QUANTUM`) 위에 있다. 격자보다 가는 호출자 bound는
    거절한다.
- `bounds.py`: 상자 kit (§4.9).
- `allocation.py`: 비중 입력(벤치마크, 다른 run이 발행한 비중)은 출처가 아니라 **선언한 불변식**으로 정의한다
  (부호, 합의 상한, 허용오차, 필요한 coverage). 검증은 소비 시점에 한다 — PIT 의미가 살아 있는 유일한 자리다. 합의
  불변식은 coverage 범위다(200종목 지수의 4종목 조각은 합이 약 0.549이고, 나머지는 현금이다).
- `netting.py`: 여러 멤버의 비중을 합칠 때 상쇄된 양을 **재기만 한다.** 결합 규칙(동일 가중, IC 가중, 위험 균형)은
  연구자의 경제적 선택이고 패키지가 정하지 않는다.
- 결측 채우기 helper(`fill_missing`)는 없다 — 0으로 채우면 "포지션 없음"을 주장하는 것이고, 평균으로 채우는 것은 연구
  판단이다.

## 8. 체결 — 의도가 주문이 되고 체결이 되기까지

### 8.1 체결 단계

한 시장 시각에 이 시각이 목표인 대기 의도가 있으면(`run/engine/stages/execute.py`):

```text
그 시각의 체결 스냅샷 (집합 단위 한 번)  →  종목 선언 관문  →  plan_orders  →  Exchange.execute
  →  체결 → 원장 항목 (domain/fill.py)  →  Account.append  →  (VALUE · OBSERVE 뒤) 피드백 증거
```

**체결 경로에는 제약 평가가 없다.** 제약은 판단 시각의 경제적 판단이다. 1주 단위 변환 때문에 뒤늦게 나타나는
초과는 체결 진단에 남고 Compliance가 잡는다(`UC-EXEC-003`). 체결은 다시 최적화하지 않는다 — 판단을 뒤집는 것이다.
`risk/` 층은 없다 — 검증은 이미 세 번 한다: preflight(§10.3), 의도 생성(§5.2), commit(§9.1).

### 8.2 조회의 세 결과

| 체결표 | 결과 |
|---|---|
| 행이 없다 | 그 종목만 0주 체결 `absent` — 그 시각에 이 거래소에 없었다 (상장 전 · 상장폐지 후). 시장 사실 |
| `is_tradable = false` | 그 종목만 0주 체결 `nontradable` — 상장됐지만 거래 불가. 시장 사실 |
| `is_tradable = true`인데 선언한 가격이 없거나 `<= 0` | **batch 실패** — 데이터 계약 결함 |

앞의 둘은 batch를 실패시키지 않는다. 3,000종목 × 250세션이면 정지와 상장폐지는 매일 있고, 그러면 run이 첫 주에
죽는다. 세 번째는 preflight가 미리 검사하므로(§10.3) run 중에 나오면 그 사이에 데이터가 바뀐 것이다.
**batch-atomic**은 전제 조건이 전부 아니면 전무라는 뜻이고(스냅샷 조회, 상장 규칙, 비용 규칙), 체결 결과는 종목마다
다를 수 있다.

### 8.3 `plan_orders` — 비중이 수량이 되는 유일한 자리

`domain/order.py::plan_orders(account, execution_time_nav, prices, weight_targets, cash_target, budget, rules,
tradable) -> OrderBatch`.

- **함수이지 Protocol이 아니다.** 구현이 하나이고 층이 닫혀 있으므로 확장점의 겉모습을 만들지 않는다.
- 전략은 가격이 움직이기 전의 평가 시각에 목표를 선언했으므로, 변환은 체결 가격과 NAV가 둘 다 알려진 **체결
  시각**에 한다. 수량 = 목표 비중 × NAV / 체결 가격이고, 체결 가치는 정확히 `w · NAV`다. 판단 시각에 계산한 수량을
  재사용하지 않는다 — 델타는 체결 시각의 committed 보유 · 현금과 그 시각의 체결표 행에서 나온다(가짜 회전율을 막는
  첫 자리).
- 매도가 먼저이고, 매수는 현재 현금 + 반올림된 매도 대금으로 조달한다. 거래소가 거절할 매도(거래 불가)는 매수 자금이
  되지 않는다. 현금이 모자라면 매수를 **델타가 큰 것부터**, 동점은 `instrument_id` 순으로 결정론적으로 자른다 —
  목표를 가장 적게 놓치는 포지션에 부족분이 떨어진다. 비례 축소는 하지 않는다(그것도 판단이다).
- 살 수 있는 수량은 비용까지 포함해 **정확히 푼다**(한 단위씩 찾지 않는다).
- 보유 종목은 언제나 가격이 선택되어 있어야 한다. 목표에만 있고 행이 없는 종목은 해석되지 않은 요청으로 남아
  거래소가 `absent` 증거를 낸다.
- `plan_orders`는 전략을 다시 부르지 않고 의도를 다시 계산하지 않는다. 판단은 최종이다.

### 8.4 Exchange — 계약은 좁고, 안쪽은 거래소의 것

- **받는 것** (`ExecutionCall`): 주문 묶음, 그 시각의 시장 상태(체결 스냅샷), 계좌 스냅샷, 종목 사전, 그 사전에 묶인
  자기 규칙. **주는 것**: 체결 결과(수량 · 가격 · 비용 · 채우지 못했으면 그 이유).
- **어떻게 채우는지는 전부 거래소 안의 일이다.** 프레임워크가 단계를 고정하려 했다가 기각됐다 — 선물(승수 · 일일
  정산 · 증거금 · 만기), 중국 A주(T+1, 계좌 이력에 의존), 채권(경과이자), 옵션(만기 정산)이 깨진다.
- **설정은 데이터다.** 거래소가 무엇을 모델링하는지(비용 · 가격제한 · 숏 처리 · `not_modelled` 목록)를
  `settings`(엄격한 JSON)로 선언한다. 스키마는 거래소의 것이고 프레임워크는 "거래소는 설정을 갖는다"만 안다. 설정은
  run identity에 접힌다 — 설정이 다르면 다른 run이다. 기록에서 세금 없는 KRX와 있는 KRX를 소스를 열지 않고 구별한다.
- 가격이 체결표의 두 번째 가격(예: 가격제한의 기준가)을 필요로 하면 `execution_requirements()`로 그 필드를 선언한다.
  거래소는 `DataRequirement` 소비자가 아니다 — 점 조회다.
- 거래소는 저장소를 모르고, 상장(어느 종목을 어떤 규칙으로)은 거래소의 얼린 설정이 소유한다. `RunDefinition`에는
  상장 필드가 없다 — 거래소를 바꾸는 것이 순수한 주입으로 남는다.

| | Academic | KRX |
|---|---|---|
| 방향 | 양방향 | 롱온리 (숏은 설정이 답한다) |
| 수량 | 분수 (상장 규칙대로) | 정수 단위 |
| 가격 | run의 `execution.trade_price` | 같다 |
| 체결 | 전량 | 지원하는 주문은 전량 |
| 비용 | 0 | 수수료 · 매도세(ETF 면제) · 현금 부족 시 자르기 |
| 설정 | `{profile: academic, costs: none, partial_fills: never}` | `KrxSettings` (비율 · 가격제한 · …) · `not_modelled` |
| 사실성 | hypothetical | simulation |

- 둘 다 `OrderBatch → FillBatch → commit → mark`를 따른다. 봉투는 공유하고 채우는 알고리즘은 나눈다.
- 공통 한계: 체결 가격이 오래된 관측인지(15:30 행에 09:00 가격) 패키지는 잴 수 없다 — profile의 선언된 한계이고, 컬럼
  이름을 경고하는 것은 에이전트의 일이다. 수량 결정과 체결은 같은 시각이다. 실제 주문지 모양이 필요하면 판단 시각에
  `self.recorder`로 기록한다 — 기록된 수량은 체결이 아니고, 체결 경로는 그 기록을 읽지 않는다.
- 이름은 사실성을 주장하지 않는다. profile은 구현한 규칙과 선언한 한계만 주장한다.
- 사용자는 profile을 상속해 상장 종목과 비용을 더할 수 있고, `execute`를 바꾸는 서브클래스는 싣기에서 거절된다(§4.6).
- 성능 경로(KRX의 빠른 길)는 결과가 같다는 것이 증명될 때만 존재한다. 사용자가 고르는 모드가 아니다.

### 8.5 FillBatch

- `Fill`은 요청 수량 · 크기를 정한 수량 · 체결 수량 · 가격 · 비용(수수료 · 세금) · 종류 · 이유를 들고, `FillBatch`는
  그 묶음과 본 계좌 버전을 든다.
- **0주 체결의 이유는 넷이다**: `absent`(그 시각에 거래소에 없었다), `nontradable`(거래 불가), `no_trade`(델타가
  0), `unfunded`(현금이 먼저 쓰였다). 0주 체결과 거절은 체결로 위장하지 않는다(`UC-CLOSED-LOOP-001`).
- 체결의 출처별 불변식(가격 × 수량 = 현금 − 비용)은 체결을 만든 쪽이 검사한다. 원장은 모른다(§9.2).
- 체결 → 원장 항목 변환은 `domain/fill.py`에 있다 — 만드는 쪽의 일이다. 계좌는 체결을 모른다.

## 9. 계좌와 평가

### 9.1 Account — 원장에 붙이는 유일한 권한

```text
append(state, entries, expected_version)          → 원장 항목을 붙인다         (체결, 앞으로의 accrual)
mark(state, prices, at)                           → 자기 보유 × 가격 = 평가를 기록한다
commit_append / commit_mark                       → 준비된 것을 실패 없이 설치한다
```

- 계좌가 판단하는 것은 셋이다: 이것이 내가 든 상태인가(버전 순서, `expected_version`), 결과가 유효한 계좌인가(현금
  음수 금지, 롱온리에 숏 금지), 한 번만 붙이는가. 검증에 실패하면 아무것도 바뀌지 않는다.
- **평가는 계좌가 직접 곱한다.** 계좌는 가격만 받고(`ObservedPrice`: 종목 · 가격 · 그 가격을 본 시각) 자기 보유에
  곱한다. 0.15.0에서는 평가 서비스가 스냅샷의 수량으로 평가를 만들고 계좌가 그 수량이 자기 보유와 같은지 다시
  검사했다 — 같은 사실을 두 곳에서 다뤘다. 계좌가 곱하면 어긋날 수가 없으므로 그 검사가 사라진다.
- 계좌는 자기가 어느 profile을 위한 것인지 모른다. "academic 계좌"나 "KRX 계좌"는 없다.

### 9.2 원장 — 한 모양, 출처 태그

계좌에 영향을 주는 것은 두 종류이고, 둘은 다른 문으로 들어온다.

| 종류 | 무엇을 바꾸나 | 만드는 쪽 | 문 |
|---|---|---|---|
| 장부를 바꾸는 것 | 현금, 수량 | 체결(Exchange) · 배당 · 쿠폰 · 이자 · funding fee · 선물 정산 · 분할(Accrual, 앞으로) | `append(LedgerEntry)` |
| 장부를 평가하는 것 | 아무것도 바꾸지 않는다. 가치만 매긴다 | 평가 (§9.5) | `mark(prices)` |

```text
LedgerEntry
    at          시각
    cash        Δ현금
    positions   {종목: Δ수량}
    origin      무엇이 만들었나   ("fill" · 앞으로 "dividend" · "coupon" · …)
    detail      출처별 상세
```

- 체결은 둘 다, 현금 배당 · 이자 · 대차 수익 · funding · 선물 정산 · 펀드 설정/환매는 현금만, 액면분할 · 무상증자는
  수량만 바꾼다 — 전부 같은 두 칸의 조합이므로 합타입이 아니라 **한 모양 + 출처 태그**로 족하다.
- **원장은 출처를 모른다.** 출처별 불변식은 만든 쪽이 검사하고, 출처를 원장 항목으로 바꾸는 것도 만든 쪽이 한다
  (`domain/fill.py`의 체결 → 항목). 그래서 쿠폰이든 funding이든 새 출처가 생겨도 `domain/account.py`는 한 줄도 바뀌지
  않는다(개방-폐쇄 원칙). 0.15.0에서는 원장 모듈이 `Fill`을 import해서 변환했다.
- 체결이 아닌 사건을 체결로 인코딩하지 않는다. 배당을 `quantity=0, cost=−배당금`인 체결로 쓰면 계좌 숫자는 맞아도
  체결 건수 · 회전율 · 비용 분석 · 체결률이 전부 거짓이 된다. `vqapr.fill` 행은 `origin == "fill"`인 항목에서만 나온다.
- **죽은 run이 남기는 것은 손상된 계좌가 아니라 짧은 이야기다.** append-only 원장의 모든 앞부분이 유효한 원장이고,
  체결 행은 commit마다 디스크로 흐른다.
- `origin`은 구조화하지 않은 라벨이다(오너 결정). 펀드 설정/환매는 NAV의 분모를 바꾸므로, 시간가중 수익률이
  필요해지는 날 "외생적 현금흐름인가"가 구조로 필요해진다(§16).

### 9.3 AccountMode — 하는 일이 하나다

`LONG_ONLY`(적용 뒤 음수 보유가 있으면 실패)와 `SIGNED`(음수 보유 허용)의 차이가 전부다. 분수 · 로트 · 반올림 ·
가격 · 비용 · 체결 시각은 모드가 정하지 않는다(§2.10). run 시작에 얼리고 도중에 바꿀 수 없다. 거래소는 거래소에
유효한 체결만 만들고, 계좌는 자기 모드와 회계 불변식으로 다시 검사한다 — 주입된 컴포넌트를 믿는 권한은 권한이 아니다.

### 9.4 현금

- **`현금 >= 0`은 모든 모드 · 모든 profile의 공통 불변식이다.** 비용 · 증거금 · 강제 청산을 모델링하지 않은 차입은 공짜
  돈 버튼이다. gross를 올리는 것은 차입이 아니다(NAV 100에 롱 2.0 / 숏 1.0이면 현금은 정확히 0). 음수 현금만 차입이다.
- 현금은 이자를 받지 않는 기준 통화다. 유휴 자금의 수익은 등록한 파생 단가 자산(`P_t = P_{t−1}(1 + r_f,t)`)을
  **포지션으로** 들어 표현한다 — 선언한 포지션은 lineage를 남긴다. 자동 이자는 생명주기 현금흐름(`UC-CASHFLOW-001`,
  미래)이다.

### 9.5 평가 — 가격 고르기는 밖에서, 곱셈은 계좌가

매 시장 시각(§3.5), 체결이 있었으면 그 체결의 스냅샷으로, 없었으면 새로 읽은 스냅샷으로 — **같은 시각, 같은 가격**.
평가는 아무것도 구독하지 않고 일정도 없다. 평가 설정(`ValuationConfig`)은 없고 확장점도 아니다 — NAV 정의가 run마다
다르면 run을 비교할 수 없다.

`domain/valuation.py`가 보유 종목마다 가격을 고른다(순수 함수).

| 그 시각의 스냅샷 | 고른 가격 | `observed_at` |
|---|---|---|
| 가격이 있는 행 | 그 가격 | 그 시각 |
| 행이 없거나 가격이 없다 (정지 · 상장폐지) | **이전 평가의 가격을 이어 든다** | **원래 관측 시각 그대로** — 다시 찍지 않는다 |
| 이전 평가도 없다 (한 번도 가격이 없었다) | 없음 — 평가에서 빠진다. 수량은 장부에 남는다 | — |

- 정지 종목을 0으로 적어 내리지도, NAV에서 빼지도 않는다 — 가격이 움직임을 멈출 뿐이다. 1년 정지된 종목이 매 시각
  새로 평가된 것처럼 보이지 않도록 `observed_at`을 다시 찍지 않는다.
- 평가할 수 없는 보유는 분모에서 빠진다. 지어낸 가격은 이후 모든 비중의 환산 기준이 된다.
- 정지와 상장폐지는 컷오프에서 구별되지 않는다(미래만이 가른다). 평가는 `observed_at`이라는 사실을 기록하고, 그 뜻은
  보고서가 정한다.
- 가격 고르기의 규칙은 종목 유형과 함께 자란다(채권의 clean/dirty와 경과이자, 선물 정산가, 환율). 그래서 계좌 밖의 한
  모듈이다. 곱셈은 계좌의 일이다(§9.1).
- **체결이 없는 시각의 평가는 원장 항목을 만들지 않고 `account_version`을 올리지 않는다.** 버전은 "계좌가 바뀌었다"를
  뜻해야 하고, 거래소 · 엔진 · Compliance의 낙관적 동시성 검사가 그 뜻에 기댄다. 평가의 identity는 찍힌 시각이다.
- **평가 실패는 체결이 commit된 뒤에 날 수 있는 유일한 실패다**(`FAILED_AFTER_COMMIT`, 정확한 계좌 버전을 기록한다).

### 9.6 계좌 이력 — 기록은 고정, 구독은 선언

- 고정된 필드: 계좌 `nav` · `cash`, 종목 `quantity` · `price` · `observed_at`. 집합이 고정이므로 "집합 밖을 요구"하면
  계산하기 전에 실패한다.
- 소비자(전략, Compliance)는 `AccountHistoryInput`으로 필드와 lookback을 선언한다. lookback은 필수다 — 없으면
  콜백마다 전체 이력, run마다 제곱이다.
- **선언이 보존을 정한다.** 누군가 선언한 만큼만 평가를 들고, 선언이 없으면 현재 평가 하나만 든다. 전체 이력은
  `vqapr.account`로 발행되고, 재구성은 메모리가 아니라 발행물을 읽는다.
- 계좌 이력은 `memory`와 독립이다 — 상태 없이도 stop-loss와 cooldown을 쓴다(`UC-ACCOUNT-HISTORY-001`).
- 0.15.0 문서가 적은 `avg_entry_price` · `realized_pnl`은 이 집합에 없다. 종목별 실현 손익은 경제적 정의(평균 원가 대
  FIFO, 비용의 원가 산입, 부분 매도, 부호 전환)가 정해질 때까지 기본 기록이 아니다(§16).

## 10. run의 일생

```text
workspace (선언이 쌓인다)  →  preflight (판정 · 얼리기)  →  engine (고리)  →  recording (기록)
                                                          └→ output (창고의 문: dataset 발행)
```

### 10.1 workspace — 명령과 명령 사이에 남는 것

- 한 프로젝트가 쌓은 선언(dataset, 컴포넌트 참조, 종목 사전, run)은 `.vqapr/workspace.yaml` 하나에 있고,
  `workspace/registry.py::Workspace`가 열고 · 조회하고 · 쓴다. 전역이 아니다 — 명시적으로 넘긴다(`qlib.init()` 같은
  프로세스 전역 provider는 없다, PRD §12.5).
- **`register`가 workspace로 들어오는 유일한 문이다.** 코드(전략 · DataModel · Compliance · 거래소)와 세상에 관한
  사실(dataset · 체결표 · 종목 사전 · run)이 같은 파일 형식으로 같은 문을 지나고, 둘 다 검증을 통과해야 기록된다.
  "등록됐지만 쓸 수 없는 것"은 남지 않는다.
- 선언 문서 하나는 트랜잭션 하나다. 순서는 명단 → 데이터 → 코드 → run(run이 앞의 것들을 가리키므로). 하나라도
  거절되면 장바구니째 버리고 workspace는 한 글자도 바뀌지 않는다. 쓰기는 끝에 한 번, 잠금 아래에서.
- 상대 경로는 선언 파일의 디렉터리 기준이다 — 코드든 데이터든. 선언과 컴포넌트가 함께 움직인다.
- 컴포넌트는 argv만으로 등록할 수 없다. 등록의 단위는 선언 파일이고 `vqapr new`가 컴포넌트 옆에 선언을 놓는다.
- 재등록(`workspace/merge.py`): 선언한 반쪽이 같으면 잰 반쪽만 갈아 끼우고, 다르면 "이미 등록된 이름"(409)이다.
- 무언가 아직 가리키는 선언은 철회할 수 없다(`workspace/references.py`).
- 점진적 구성이 표현되어야 한다(PRD §12.1): 종목 · 체결 가정 같은 결정을 에이전트 대화에서 하나씩 정할 수 있다.

### 10.2 RunDefinition

```yaml
runs:
  factor-run:
    writes: factor-weights          # 필수. 이 run이 창고에 넣을 dataset의 이름만
    strategy: {component: factor}   # 또는 datamodel: {component: …, value_fields: […]} — 모델은 하나
    instruments: [...]              # 등록된 종목 사전
    timezone: Asia/Seoul
    start: '2022-01-12T00:00:00+09:00'
    end:   '2022-01-25T23:59:59+09:00'
    schedule: {every: 1d, at: '08:00'}   # 부품의 시계 (§3.2)
    exchange: sample-exchange       # 도구: 등록된 거래소 (전략 run)
    execution:                      # 체결표 = 시장 시계
      dataset: sample-execution
      trade_price: close
      fill: {at: '15:30'}           # FillRule (§3.4)
    compliance: [no-short]          # 도구: 0개 이상 (전략 run)
    initial_account: {cash: '100000000', mode: SIGNED, positions: {}}
```

- **run은 모델 하나다.** 여러 모델은 여러 run이고, `--jobs N`이 run들을 병렬로 돈다. 같은 조건에서 돌렸는지는
  선언이 아니라 사후에 얼린 층의 identity로 확인한다 — 주장 대신 증거.
- **`writes`는 필수이고 이름만 적는다.** 선언한 것만 창고에 들어가고, 계좌(기록)는 언제나 생긴다. 스키마는 이미
  소비자의 `DataRequirement`가 말한다. 남의 이름이면 `run.output_registered`로 거절하고, 이 run의 이전 출력이면
  `--force` 없이는 계산 전에 거절한다(record와 dataset을 한 손잡이로). 등록된 컴포넌트 버전과 다른 버전이 만든 출력은
  `run.output_stale`(412)이다.
- run identity에 접히는 것: 일정 전개, 시장 시계의 원천, `FillRule`, 거래소 지문과 **설정**, Compliance 규칙들의
  identity, 종목 사전, 초기 계좌, `writes`.
- 필드 이름은 저장 철자이지 공개 시그니처가 아니다. 규범은 run이 부품 하나와 그 시계, 시장 시계의 원천, 붙는 도구들,
  만드는 것의 이름을 말하고, preflight가 그것을 덮어쓸 수 없게 얼린다는 것이다.
- run을 얼린 뒤 workspace가 바뀌어도 그 run은 바뀌지 않는다(`UC-CONFIG-001`). 얼린 입력은 완전하다 — 실행과 재현은
  workspace를 다시 읽지 않는다.

### 10.3 preflight — 판정과 얼리기, 한 문

```text
preflight(workspace, definition) -> RunVerdict            run/preflight/verdict.py
    facts   = RunFacts(workspace, definition)              schedule · 체결표 · horizon · 컴포넌트 · 거래소 — 명령당 한 번
    checks  = 판정 일곱 (모아서 답한다)                     run/preflight/checks.py
    frozen  = freeze(facts)  또는  freeze 가 낸 거절        run/preflight/freeze.py
    → RunVerdict(거절들 · 답하지 못한 판정 · FrozenRun 또는 거절 · RunResources)
```

- `vqapr check`, `vqapr run`, Python의 `run`, `--jobs`의 모든 worker가 이 문을 지난다. **`check`가 거절하는 run은
  `run`도 배치도 거절하고 기록을 쓰지 않는다.**
- 판정과 얼리기는 둘이다 — 판정은 서로 독립인 결함을 **전부 모아서** 보고하고(한 번에 고칠 수 있게), 얼리기는 값을
  만들다 첫 거절에서 멈춘다. 둘은 같은 `RunFacts`를 읽는다. 사실 읽기가 실패하면 그 실패를 묻는 모두에게 다시 준다 —
  같은 이유로 막힌 판정은 전부 `blocked`로 원인과 함께 실린다. 판정이 답하지 못하고 얼리기가 같은 결함을 거절하면
  봉투는 둘 다 싣는다(오너 결정 2026-09-04).
- 판정: 종목 집합 · 종목 사전 · 기간 · 체결 순서(모든 판단 뒤에 체결할 시장 시각이 있나 — run이 실제로 걷는 구간만) ·
  읽을 dataset들(등록 때 그대로인가 — 지문 대조) · 비중 · 출력.
- 얼리기가 확인하는 것: `start` · `end`에 시간대가 있고 `start <= end`, 일정 전개(유일한 id, 결정론적 순서, 명시적
  IANA zone, 모호하거나 없는 현지 시각의 해소), 시장 시계가 조회 가능, 종목 선언이 하나 이상, 모든 컴포넌트의
  `inputs()`가 충족 가능, 방향과 허용 방향 · 모드의 호환, 초기 계좌 불변식, `initial_model_memory`가 모델과 호환(payload
  왕복이 같은 bytes), 규칙 id 대조, 거래소 설정이 엄격한 JSON. 체결이 있는 run은 `trade_price` 컬럼이 있고
  `is_tradable = true`인 행의 가격이 유한한 양수인지 — 이것이 §8.2의 유일한 batch 실패 조건이라 run 중이 아니라 여기서
  실패해야 commit이 남지 않는다.
- preflight는 모든 판단에 체결 목표를 요구하지 않는다. 목표는 `Rebalance` 뒤 수락 단계에서 해석한다(§3.6).
- **run은 문이 만든 것을 받는다**(`RunResources`): 판정이 실은 전략 · 거래소 · 규칙 인스턴스와 잘라 둔 체결 기간을
  그대로 넘긴다. run 시작에 다시 import하거나 다시 스캔하지 않는다. 다른 run의 봉지는 거절한다.

### 10.4 engine — 고리

- `run/engine/loop.py`: `RunLoop.run` = 시작 → 사건을 정렬해 한 번 걷기 → 끝. `ScheduledEvent`는 부품의
  `dispatch`(decide 또는 compute)로, `MarketEvent`는 `MarketClock.at`(§1.1의 다섯 줄)으로 간다. 전략 run과 DataModel
  run은 같은 루프이고 조립만 다르다(`strategy_loop`: 부품 + 시장 시계, `datamodel_loop`: 부품만).
- `run/engine/stages/`: 배선표의 행마다 한 파일. 파일 이름이 곧 컴포넌트의 메서드다 — `decide.py`가
  `StrategyModel.decide`를, `compute.py`가 `DataModel.compute`를, `execute.py`가 `Exchange.execute`를,
  `observe.py`가 `Compliance.observe`를 부른다. `accrue.py`는 자리, `value.py`는 프레임워크 자신의 단계다. 각 단계는
  `(MarketInstant) -> MarketInstant` — 앞 단계가 남긴 것을 받아 자기 필드를 채워 넘긴다.
- `run/engine/run_state.py`: 받아들여진 상태(계좌 · 모델 memory · 대기 의도)의 뿌리. 전이는 한 곳을 지난다.
- `run/engine/calls.py`: 컴포넌트가 받는 Call의 구현(§4.4).
- `run/engine/output.py`: 창고의 문(§10.5).
- 상태 기계: `CREATED → PREFLIGHTED → RUNNING`. 일정 사건마다 `상태 복원 → 창 → 결정`, 그리고 `Hold → 모델 상태
  commit` 또는 `Rebalance → 판단 시각 도장 → 체결 목표 해석 → 모델 상태 + 판단 증거 + 최신 대기 의도 commit`. 시장
  시각마다 `ACCRUE → (대기 의도가 이 시각이면) 스냅샷 → 종목 선언 → 주문 계획 → 거래소 체결 → 계좌 준비 → 계좌 commit →
  (언제나) 평가 선택 → 평가 → 계좌 평가 → (체결이 있었으면) 피드백 → (규칙이 있으면) OBSERVE`. 끝에 `FINALIZE`.
- 실패 등급: 콜백 수락 전 실패는 이전 모델 상태와 대기 의도를 남긴다. 계좌 commit 전 실패는 `PRE_COMMIT`(계좌 무변경).
  commit 뒤 발행 실패는 `FAILED_AFTER_COMMIT`(계좌 버전 기록). 중단된 run을 이어서 돌리는 것은 범위 밖이다
  (`UC-RECOVERY-001`) — 처음부터 다시 돈다.
- 엔진은 전략의 판단 cadence를 모른다. 경제 규칙을 소유하지 않는다 — Compliance의 판정 규칙은 각 규칙에, 허용오차는
  `observe` 단계에 한 번 있다.

### 10.5 창고의 문 — 출력이 dataset이 된다

- DataModel run의 행은 세션마다 형 검사를 받고 메모리에 모였다가, 마지막 세션이 끝나면 **parquet 하나**로
  `.vqapr/materialized/<dataset_id>/`에 굳고, **등록과 같은 문**(`verify_source`)을 지나 dataset으로 등록된다 —
  "어느 run의 어느 코드 버전이 만들었다"와 함께. 먼저 실패한 run은 읽을 수 있는 출력을 남기지 않는다.
- 행의 `available_at`은 §6.8대로 프레임워크가 찍는다. 출력에서 look-ahead가 발견되면(유도된 `available_at`이 행을
  만든 평가 시각보다 앞서면) 거절한다.
- 전략 run은 기록을 쓴 **다음에** `writes`로 비중을 발행한다: `vqapr.weight` 행을 그 판단의 사건 시각에 찍고, 수 데이터
  평면의 형식(DOUBLE)으로(정확한 값은 기록에 남는다). 모든 세션에서 `Hold`한 전략은 발행하지 않는다 — 형식 없는 빈
  dataset은 거짓이다. 이것이 발행된 배분과 등록된 벤치마크를 같은 종류의 입력으로 만든다(§7.5 `allocation`).

### 10.6 조립 · 명단 · 배치

- `run/assemble.py`: run 하나 — 얼린 run과 `RunResources`를 받아 저장소(run 기간) · 기록기 · 계좌 · 루프를 조립하고
  돌린 뒤, 기록을 굳히고(`run/recording.py`) 출력을 발행한다.
- `run/roster.py`: run 시작에 종목 사전을 **새로** 읽는다(얼리지 않는 것은 의도다 — 사전은 날마다 자라고, 새 이름을
  쓰지 않는 run까지 막을 이유가 없다). 그날 사전의 지문을 기록에 적는다. run 도중의 `register`가 기록을 체결이 분류된
  적 없는 지문으로 바꾸지 못하게, 기록은 이 한 번의 읽기에서 쓴다.
- `run/batch.py`: `--jobs N` — worker를 띄우기 전에 run마다 무엇을 읽는지 한 번 묻고, 한 run이 배치 안 다른 run이
  쓰는 것을 읽으면 배치 전체를 거절한다(병렬이면 순서를 약속할 수 없다). dataset마다 cube를 굽고, worker는 문자열과
  bool만 받아(`spawn` 경계) 단일 run과 똑같이 `preflight`를 지난다. worker의 BLAS는 1 스레드다. 배치가 끝나면 성공이든
  실패든 cube를 지운다. 봉투의 `jobs`는 실제로 돈 프로세스 수다.

## 11. 증거와 실패

### 11.1 증거는 영수증이지 권한이 아니다

생명주기 증거의 사슬: 일정 identity와 구간 → 현재 사건 · 평가 시각 → 전략의 결과 → 엔진이 찍은 판단 시각 →
`FillRule` 목표와 스냅샷 → 소비된 대기 의도 → `OrderBatch` → `FillBatch` → `LedgerEntry` → 계좌 버전들 →
`MarkBatch` → Compliance의 발견 → 피드백 · 한계. 발행물은 내용 · 메타데이터 · 목록 기록이 **전부** commit된 뒤에만
보인다(`UC-ARTIFACT-003`). 산출물은 생산자의 사적 클래스 없이 형 있는 객체로 읽힌다(`UC-ARTIFACT-001`).

### 11.2 기록기 — 저자가 선언하는 표

- 모델은 `tables()`로 `TableSpec`을 run 시작 전에 선언하고, 콜백 동안 `self.recorder`에 행을 쓴다. 스키마는 이식
  가능한 스칼라뿐이다. DataModel과 StrategyModel이 같은 길을 쓴다. 선언하지 않은 표에 쓰면 거절하고, 스키마 위반은
  조용히 버려지는 행이 아니라 run 실패다.
- **엔진이 다섯 봉투 컬럼을 찍는다**: `run_id` · `producer_id` · `stage` · `event_time` · `sequence`. 생산자는 위조할
  수 없고, `TableSpec`이 이 이름을 선언하면 run 시작 전에 실패한다. `vqapr.` 접두사의 표 이름도 예약이다.
- `stage`는 누가 돌았나가 아니라 **어느 시계의 시각인가**를 말하고, 닫힌 집합이다(DataModel 계산, 전략 콜백).
- 한 호출의 행은 그 작업의 commit 경계를 통과한 뒤에만 증거가 된다 — 수락 실패면 staging과 함께 버려진다.
- 기록기는 상태가 아니다: 되읽을 수 없고, 결과를 바꿀 수 없고, `load_payload()`의 원천이 아니다.
- 체결 코드에는 자유 형식 기록기가 없다 — 체결 진단은 이미 `FillBatch`에 구조로 있다.
- **기록 표는 수익의 출처가 될 수 없다.** 성과를 보고하는 데 쓰는 진단 표는 척추를 우회한다.
- 기록된 표는 run이 끝난 뒤 평범한 dataset으로 읽힌다 — 새 읽기 경로는 없다. run은 구조상 자기 기록을 되읽을 수 없다.

### 11.3 run 기록 — 디스크에 무엇이 남나

```text
.vqapr/
  workspace.yaml · instruments.json
  materialized/<dataset_id>/all.parquet               창고 — run 출력 dataset
  runs/<run-id>/
    run.json                                          run의 설정 (모든 모델이 공유한 것)
    strategies/<id>@<fp8>/strategy.json               전략 하나의 기록
                          tables/<table>/all.parquet  표마다 파일 하나, run이 끝날 때
    datamodels/<id>@<fp8>/datamodel.json · tables/
  cubes/                                              --jobs 배치 동안만
```

- 기록기는 run id를 잠금으로 잡고, 행 조각을 Arrow 버퍼에 받아, run이 끝나면 표마다 parquet 파일 하나로 봉인하고,
  완료를 표시하는 기록을 마지막에 쓴다. 아주 큰 run은 도중에 흘려 쓴다(spill). 잠금은 초당 한 번 "살아 있다"를 찍고,
  120초 갱신이 없으면 죽은 run으로 본다.
- 인덱스 파일 없이 디렉터리를 훑는다 — 인덱스 파일은 두 프로세스가 각자 읽고 각자 쓰는 경쟁을 만든다.
- 타입은 파일 안에서 이동한다(시각은 시간대가 있는 `timestamp`, 숫자는 `Decimal`로 되읽힌다).

| 프레임워크 표 | 행 | 컬럼 |
|---|---|---|
| `vqapr.account` | 평가마다 계좌 행 하나 + 보유마다 한 행 | instrument · cash · nav · quantity · price · observed_at · account_version |
| `vqapr.fill` | 체결 · 0주 체결마다 | instrument · kind · account_version · requested_quantity · sized_quantity · dealt_quantity · price · cash_delta · commission · tax · reason |
| `vqapr.weight` | 판단 · 종목마다 | instrument · weight |
| `vqapr.monitoring` | 규칙마다 시장 시각마다 | rule · passed · measured · bound · excess · verdict · tolerance · offenders · account_version |

- `strategy.json`은 run의 배선을 적는다: `schedule` 블록, `compliance` 규칙들(id · 지문), `exchange`(component_id ·
  지문 · 설정), 그리고 컴포넌트마다 **등록된 지문과 실제로 실은 지문**. 등록 뒤 컴포넌트 소스가 바뀌어도 run은
  거절되지 않고 돈다 — 지문은 관문이 아니라 **영수증**이다(`docs/issues/archive/009`). 그래서 두 지문을 나란히 남겨
  기록이 오래된 지문을 권위 있는 척하지 않게 한다. 기록은 컴포넌트 지문으로 주소가 매겨지므로(`<id>@<fp8>`) 몇 번
  고쳤는지를 디렉터리 수로 센다.
- `record/`는 `run/`을 import하지 않는다 — 기록만 읽는 프로세스(`list`, `show`, `report`)는 엔진을 import하지 않는다.
  엔진 값을 기록 모양으로 바꾸는 것은 엔진 쪽의 `run/recording.py`다.

### 11.4 보고서

- `report/`는 끝난 기록만 읽는다. **run이 저장하지 않은 것은 계산하지 않고, 새 포트폴리오 수익을 만들지 않는다**
  (`UC-RETURN-001`). 가격 dataset을 읽어 수익을 만드는 경로가 없다. NAV · 수익률 · 낙폭은 `vqapr.account`의 평가에서만
  나온다(`report/metrics.py`는 평가 기록 타입만 받는다) — 보고서의 숫자와 원장의 숫자가 어긋날 수 없다.
- 시간 격자는 `vqapr.account`의 계좌 행(평가 한 번에 한 행)이다. 체결은 계좌 버전으로 기간에 배정한다 — 두 표의 시계를
  비교하는 것은 추측이지만 버전은 commit 순서라 정확하다.
- 모든 숫자는 `Decimal`이다. 보고서는 intended · requested · dealt · committed · marked를 나란히 둔다(`UC-REPORT-001`).
- 패키지는 값과 기계가 읽는 렌더러만 준다. 시각화 라이브러리는 의존성에 없다 — 그림은 사용자가 같은 값 위에 짓는다.
- `vqapr export`는 한 전략 기록을 파일로 넘긴다(보고서의 NAV 격자 · 체결 · 비중 · 보유 · 표 · `report.json`).

### 11.5 실패 — status, stage, code, cause

첫 사용자가 에이전트이므로 실패는 읽는 것이 아니라 **파싱하는 것**이다. 그리고 자기 준비를 고치려면 문제를 한 번에
다 받아야 한다 — 그래서 예외 하나가 `Failure` 여럿을 담는다.

| 필드 | 뜻 | 집합 |
|---|---|---|
| `status` | **누가** 고쳐야 하나. 4xx = 제출물(선언 · 인자 · 데이터 · 전제)이 틀렸다, 고치기 전엔 재시도가 무의미. 5xx = 제출물은 맞고 돈 것이 실패했다 | 닫힘: `400 invalid` · `404 missing` · `409 conflict` · `412 precondition` · `422 contract` · `423 locked` · `500 internal`(프레임워크) · `502 crashed`(사용자 코드) · `503 unavailable`(기계) |
| `stage` | 어느 작업 중이었나 | 닫힘: `usage` · `open` · `read` · `register` · `lookup` · `remove` · `write` · `load` · `check` · `freeze` · `run` · `record` |
| `code` | 상황, `<주제>.<세부>` | 열림(beta). 모르는 code는 status로 처리한다(HTTP의 x00 규칙) |
| `cause` | 실제로 일어난 것 전부: 예외 타입 · 메시지 · 자르지 않은 traceback · `where`(`file:line (function)`) · `origin`(`user`/`framework`) | 모든 실패에 있다 |

- 분류되지 않은 예외는 `code: unhandled`이고, traceback의 가장 안쪽 비-인터프리터 프레임이 사용자 파일이면 502,
  패키지 안이면 500이다.
- 봉투(`VqaprError.as_dict`): `stage` · `mutation`(commit 뒤의 실패일 수 있나 — 평가 단계의 실패만 true일 수 있고
  그때 정확한 계좌 버전을 기록한다) · `retry_precondition` · `correlation_id` · `failures`. 각 실패는 `requirement` ·
  `observed` · `fix`를 든다 — 무엇이어야 했고, 무엇이 있었고, 무엇을 하라.
- **패키지는 판정하고, 대화는 skill이 한다.** 봉투의 `fix`는 명령 한 줄이고, 회복의 설명은 skill의 몫이다.

## 12. 표면 — 사람과 에이전트가 닿는 곳

`public.py` · `cli/` · `agent/`는 층이 아니라 **표면**이다. 고리의 정보 흐름에 참여하지 않고, 사용자와
에이전트가 이 시스템에 닿는 지점이다. 헥사고날로 말하면 같은 코어에 붙은 입구다 — 셸용(`cli/`)과
Python용(`public.py`).

### 12.1 `public.py` — 유일한 Python 표면

사용자와 에이전트가 import하는 곳은 여기 하나다(Facade). 저자가 상속하는 계약(`component/`의 base들),
선언 타입, 조작(`register_*`, `run`, reader, report)을 모두 여기서 다시 내보낸다. **모듈 경로는 공개 계약이
아니다.**

**단일 저자 표면**: 0.15.0에는 저자 표면이 둘이었다 — `vqapr.authoring`과 `vqapr.public`이 같은
`Rebalance`를 내보냈다. 깨지는 릴리스에서 `vqapr.authoring`을 없애고 `vqapr.public` 하나로 모은다.

### 12.2 `cli/` — 파일 목록이 곧 명령 목록

```text
main.py       파서와 라우팅.  동사마다 한 줄 요약
envelope.py   모든 명령이 내는 JSON 봉투 한 모양
new.py · register.py · check.py · run.py · list_.py · show.py · export.py · rm.py · skill.py
```

- **봉투는 성공과 실패가 같은 모양이다**: `ok · stage · failures[code · status · requirement · observed · fix]`.
  첫 사용자가 에이전트이므로 파싱 경로가 하나여야 한다.
- **사용법은 CLI가, 회복은 skill이 말한다.** `--help`는 "이 명령이 무엇이고 무엇을 받는가"에 문서 없이
  답한다. 어떻게 회복하는가는 skill이 말한다 — CLI가 회복법을 지어내면 버전 없는 두 번째 authority가 된다.
- **CLI는 `public`과 application 층(`workspace`, `run`, `record`, `report`, `agent`)과 `domain.errors`만 import
  한다.** `domain`·`data`·`component`의 안쪽으로 직접 들어가지 않는다. 0.15.0의 CLI는 `public`을 세 파일에서만
  거쳤고 나머지는 안쪽을 직접 import했다 — 입구 둘이 각자 코어로 들어가 "한 문"이 깨져 있었다. 경계 테스트가
  이 규칙을 지킨다.

### 12.3 `agent/` — 엔진이 부르지 않는 것

```text
skillset.py   출하하는 skill 집합, 설치본이 출하본 그대로인지의 판정 (내용 해시)
skills/       SKILL.md 들과 그 스크립트 — 에이전트가 읽는 사용설명서
sample/       `vqapr new sample` 이 만드는 예제 프로젝트
```

패키지는 결정론적으로 판정하고, 대화는 skill이 한다(PRD §2.6).

### 13.2 층

괄호 안의 숫자가 층이다. **모듈은 자기보다 엄격히 낮은 층만 import한다** — 같은 층끼리도 안 된다(같은 층을
허용하면 `a → b`와 `b → a`가 둘 다 합법이 되고, 그것이 막으려는 순환이다). 층 사이 간격이 10인 것은 사이에 끼울
자리를 남기기 위해서다.

| 층 | 무엇 | 왜 여기 |
|---|---|---|
| 0 | `domain` · `_internal` | 아무것도 import하지 않는다. 모두가 읽는다 |
| 10 | `data` · `signals` · `portfolio` · `record` | 한 주제씩. 어휘(`domain`)만 읽는다 |
| 20 | `component` | 저자가 보는 계약. 데이터 요구사항 · 기록기 · kit을 읽는다 |
| 30 | `workspace` | 선언을 등록할 때 컴포넌트를 싣고 데이터를 잰다 |
| 40 · 45 · 50 | `run.preflight` · `run.engine` · `run` | 출발 전 → 고리 → 조립 · 기록 변환 · 배치 |
| 60 | `report` | 끝난 기록만 읽는다 |
| 90 · 95 · 100 | `public` · `agent` · `cli` | 표면 |

필요한 것이 위층에 있으면 대개 **값이 잘못된 곳에 있는 것이다** — 의존을 올리지 말고 값을 내린다.
`tests/boundaries/test_the_layers_hold.py`의 `LAYERS`가 이 표를 들고 있고, 선언된 예외(`OPEN`)는 비어 있어야
한다.

### 13.3 기계가 지키는 규칙

| 규칙 | 테스트 |
|---|---|
| 층은 엄격히 아래로만 | `tests/boundaries/test_the_layers_hold.py` |
| 같은 파일 이름은 같은 역할일 때만 — 허용 목록 `{base.py}` | 파일 이름 경계 테스트 (캠페인이 추가) |
| CLI는 `public` · application 층 · `domain.errors`만 | CLI import 경계 테스트 (캠페인이 추가) |
| 표준 라이브러리 모듈 이름을 가리지 않는다 (`time`, `signal` …) | ruff `A005` |
| `public.py`가 내보내는 이름의 고정 | 기존 export 고정 테스트 |
| 함수 지역 import에는 이유가 적힌다 | `tests/boundaries/test_a_deferred_import_states_its_reason.py` |

### 13.4 이름 규칙

- **이름은 그것이 무엇을 하는지 말한다.** 독자가 이미 아는 어휘를 쓴다 — DDD의 `domain`, OOP의 `base`,
  DES의 `event`·`schedule`·`clock`. 그림의 비유(화살표, 문, 도시락)는 설명에는 쓰되 이름에는 쓰지 않는다.
- **개념 하나 = 모듈 하나. 모듈 이름은 안의 주 클래스, 단수.** (`instrument.py`, `account.py`)
- **base 클래스와 구현은 다른 파일이다.** 확장점의 base는 `base.py`, 구현은 그 옆.
- **패키지와 같은 이름의 모듈을 두지 않는다** (`account/account.py` 같은 것).
- **폴더는 주제로 가른다.** 기술적 성질("순수 함수라서")이나 호출 방향("저자가 부르니까")으로 가르지 않는다.
- **모듈 docstring은 지금 무엇을 하는지 말한다.** "어디서 옮겨 왔나"는 implementation record와 git의 몫이다.
  지금도 유효한 이유는 남긴다.

### 13.5 만들지 않는 것

| | 왜 |
|---|---|
| `utils/` · `helpers/` · `common/` | 내용을 말하지 않는 이름에는 무엇이든 쌓인다. 공통 어휘의 자리는 `domain/`이다 |
| `toolkit/` · `operations/` | 주제가 아니라 호출 방향이나 성질로 붙인 이름. `operation`은 이미 다른 뜻으로 쓰였다 |
| `config/` | 선언 타입은 소유자 옆에 산다(`DatasetRegistration`은 `data/`, `FillRule`은 `domain/fill.py`, `RunDefinition`은 `workspace/`). 모아 보이는 일은 `public.py`가 한다 |
| `workflow/` | 실험 관리를 패키지가 소유하지 않는다. run은 값이고 기록은 증거다 |
| `contrib/` | 확장을 패키지 안에 두면 사용자 코드가 패키지에 쌓인다 |

### 13.6 테스트

`tests/`는 위 패키지를 1:1로 미러한다. 어느 한쪽에만 있는 디렉터리는 그 자체로 질문이다. 층 하나로 성립하지
않는 것이 더 붙는다: `tests/acceptance/`(여러 층을 지나야 성립하는 시나리오), `tests/boundaries/`(없어야
하는 것이 없음), `tests/characterization/`(거절 어휘의 baseline), `tests/qa/` · `tests/showcases/`. UC 추적은
디렉터리가 아니라 `@pytest.mark.uc("UC-…")` 마커로 한다.

## 14. 시나리오 — 데이터가 어떻게 흐르나

아래 흐름은 0.14.3 stepper(`docs/walkthroughs/2026-09-11-scenario-stepper-0.14.3.html`)가 `sys.setprofile`로
기록한 실제 호출 순서를, 이 문서의 모듈 이름으로 옮긴 것이다.

### 14.1 데이터 등록 — `vqapr register sample.yaml`

YAML 한 장에 명단 · 가격표 · 체결표 · 전략 코드 · run이 적혀 있다. vqapr은 그대로 믿지 않는다. 파일을 실제로
열어 선언대로인지 재고 지문을 남기고, 코드를 실제로 import해 규격을 본 뒤에야, 장부를 **한 번** 쓴다. 하나라도
거절되면 아무것도 쓰지 않는다.

```text
cli/register → workspace/registration.apply
  Workspace.transaction                         workspace/registry
   ├ 명단     verify_roster → build_roster        data/verification → domain/instrument
   ├ 데이터   verify_source: 컬럼 → 키 → 기간 → 값 → 체결 가격 → 지문   data/verification (여는 것은 data/scan)
   ├ 코드     fingerprint → conformance            component/
   ├ run      RunDefinition                        workspace/run_definition
   └ commit → .vqapr/workspace.yaml 한 번
cli/envelope.success
```

### 14.2 DataModel run — `vqapr run features-run`

날마다 종목별 지표를 계산한다. 사고파는 것이 없으므로 **시장 시계가 없고** 일정 시계만 있다. 루프는 전략 run과
같은 `RunLoop`이고 부품만 다르다. 결과 행은 끝에 parquet이 되어 **등록과 같은 문**을 지나 dataset이 된다.

```text
cli/run → run/preflight/verdict.preflight (판정 + 얼리기)  → RunResources (문이 실은 모델을 그대로)
run/assemble
  → data/store (horizon = run 기간 + lookback)
  → run/engine/loop.datamodel_loop → RunLoop.run
       ScheduledEvent 마다: stages/compute → 창 (data/window · data/panel) → 저자의 compute() → Rows
                           → engine/output.append (available_at 은 프레임워크가 찍는다)
  → engine/output.register → data/verification.verify_source → Workspace commit
  → run/recording → record/writer
```

### 14.3 전략 run — `vqapr run factor-run`

```text
[출발 전]  preflight: facts 를 한 번 읽고 → checks 일곱 → freeze → FrozenRun
[조립]     run/roster (명단 새로 읽기) · data/store · record/writer 켜기 · 계좌 (초기 현금) · loop
[고리]     08:00  ScheduledEvent  stages/decide
                    memory 복원 → 창 (전날까지만 보임) → 저자의 decide() → Rebalance
                    → 도장 (체결 목표 = 결정 다음 첫 시장 시각, domain/fill.FillRule) → 대기 의도 하나
           15:30  MarketEvent     stages/accrue  (자리만)
                                  stages/execute  plan_orders (domain/order) → Exchange.execute → Account.append
                                  stages/value    select_prices (domain/valuation) → Account.mark
                                  stages/observe  Compliance.observe → vqapr.monitoring
[도착 후]  run/recording → record/writer (.vqapr/runs/<run>/strategies/<id>@<fp8>/)
           비중 발행 → engine/output.register → 같은 문 → dataset 등록
```

**이 구조가 지키는 것**: 전략은 결정 시각 이전 데이터만 보는 창을 받고, 체결은 결정 **다음** 시장 시각에만
일어나며, 같은 시각이면 시장이 먼저다 — look-ahead가 구조적으로 불가능하다. NAV는 계좌 한 곳에서만 나온다.
check와 run은 같은 문(`preflight`)을 지나므로 같은 답을 낸다. 두 시계가 시작 전에 확정되고 run이 얼려지므로 같은
입력은 같은 결과를 낸다.

### 14.4 저장된 비중을 읽는 전략 — enhanced index

14.3이 발행한 비중(`factor-weights`)을 alpha로 읽고, 동일가중 벤치마크에 그 절반을 더해 0 아래를 잘라 롱온리로
만든다. alpha가 공개되는 08:00보다 뒤인 09:00에 판단한다. 얼리기에서 run이 만든 표와 벤더 표가 **똑같이** 지문
한 번으로 묶인다. "출력은 곧 dataset"이라는 한 규칙 덕분에 전략 위에 전략을 쌓는 데 새 부품이 필요 없다.
enhanced index는 패키지의 부품이 아니라 사용자 전략이다 — `portfolio/bounds.py` · `portfolio/optimize.py` ·
`component/compliance/single_name_cap.py` · `component/exchange/krx.py`(ETF 매도세 면제)를 쓴다
(`showcases/show_005_enhanced_index/`).

### 14.5 `--jobs` 배치

`run/batch`가 worker를 띄우기 전에 run마다 무엇을 읽는지 한 번 묻고, 한 run이 다른 run이 만드는 것을 읽으면
배치 전체를 거절하고, 읽을 표를 한 번 굽는다(`data/cube`). worker는 단일 run과 똑같이 `preflight`를 지나 판정을
받고, 스캔 대신 구운 파일을 메모리 매핑한다. 끝나면 구운 파일은 지워진다.

|---|---|---|---|
| 16-1 | 현금을 종목으로 볼 것인가 | 이자 없는 기준 통화. 이자는 파생 단가 자산을 포지션으로 든다(이미 "반쪽 종목"). 바꾸지 않는 이유: 현금을 종목으로 두면 `SIGNED`가 공짜로 차입하게 되고(숏과 차입이 결합), 현금은 정의상 가격 1이라 정말 특별하다 | **증거금**(차입 = 금융 자산의 숏, 비용은 drift) 또는 **다통화**(KRW · USD를 종목으로 두면 환전은 두 종목의 교환) |
| 16-2 | 유도된 거래 가능 여부(`거래대금 > 0`)로 돈 run을 실제 정지 이력으로 돈 run과 어디까지 비교 가능하게 볼 것인가 | 고른 규칙이 얼린 입력이고 한계가 결과에 기록된다 | 같은 전략을 두 dataset으로 비교하는 실제 사례. 후보: 그대로 / 규칙이 다른 run의 비교에 경고 / 별도 사실성 표시 |
| 16-3 | 필드별 저장에서 `CoverageRequirement`에 필드 축이 필요한가 | coverage는 종목별("이 이름이 기간 안에 N개") | 모델이 실제로 `CoverageRequirement`를 쓸 때 |
| 16-4 | live로 가면 이 층 구조가 살아남나 | 층은 "판단 시각 ≠ 체결 시각"에 기대고, live는 그 간격을 없앤다(접근 제한 §2.3과 델타 유예 §8.3이 약해진다) | live를 열기 **전에** 답해야 한다. 후보: 좁은 구조 유지 / nautilus `Environment` 같은 주입 / 영구 범위 밖 |
| 16-5 | `writes`는 하나인가 목록인가 | 하나 | DataModel이 한 번의 계산으로 여러 dataset을 내는 경우 |
| 16-6 | 원장의 `origin`을 구조화할 것인가 | 구조 없는 라벨 | 시간가중 수익률이 필요해질 때 — 펀드 설정/환매는 NAV 분모를 바꾸므로 "외생적 현금흐름인가"가 구조로 필요해진다 |
| 16-7 | 기간에 따라 바뀌는 비용 비율 | 비율은 거래소 설정의 상수. 비율이 바뀐 기간은 다른 거래소 설정 · 다른 run | 한 run 안에서 세율이 바뀌는 연구(예: 증권거래세 인하 전후를 한 번에) |
| 16-8 | 종목별 실현 손익을 기본 기록으로 둘 것인가 | 기본이 아니다. 경제적 정의가 없다(평균 원가 대 FIFO, 비용의 원가 산입, 부분 매도, 부호 전환) | 보고서가 종목 귀속을 넘어 실현 손익을 요구할 때 |
| 16-9 | 결합 결과가 멤버마다 실제 상태의 identity와 반영 범위(계좌 버전 범위 · 사건 범위 · 컷오프)를 보존해야 한다 | 요구사항이지만 부분만 구현됐다 — 경로 이동 여부(`moved`/`constant`)와 원천 id 목록만 발행한다. **충족된 요구로 읽지 말 것** | 앙상블의 근사 크기를 값으로 검사해야 할 때 |
| 16-10 | `Budget`의 이름 | 내용은 방향 · 현금 범위 · 비중 범위. 퀀트에서 budget은 흔히 위험 예산을 뜻해 이름이 약하다 | 다음 깨지는 릴리스 |
| 16-11 | domain의 `Panel` Protocol이 필요한가 | component가 data보다 위층이므로 구현(`data/panel.py`)을 직접 가리킬 수 있다 | 개념 트리 캠페인의 data 단계에서 확인 |

**닫힌 것** (다시 열지 않는다): 전략은 미래 일정을 보지 않는다(§3.4 · §7.1). `RowsLookback`은 pivot된 표의 행을
센다(§6.4, 2026-09-01). run은 모델 하나다(§10.2, record `201`). 지문은 관문이 아니라 영수증이다(§11.3). `Hold`는
아무것도 예약하지 않는다(§3.6).

## 17. 인수 조건

재작성은 이 목록이 characterization 테스트로 닫힐 때 끝난다. 0.15.0 문서의 목록에서 뒤집히거나 대체된 것은 코드의
현재 의미로 고쳐 적었다.

**시간과 사건**

1. 두 showcase(Academic 롱숏, KRX 롱온리)가 같은 `RunLoop`과 같은 사건 순서를 쓴다.
2. 콜백 결과는 `Hold | Rebalance`이고, `Hold` · 수락된 `Rebalance` · 0주 체결이 구별된다.
3. 얼린 일정의 04:00 사건은 관측 행이나 체결 행이 없어도 콜백을 부른다.
4. 같은 시각이면 시장 시계(ACCRUE → EXECUTE → VALUE → OBSERVE)가 판단보다 먼저다.
5. 체결 목표는 `체결 시각 > 판단 시각`과 포함 `[start, end]`를 지키고, 등호 예외가 없다.
6. 목표 해석 실패는 모델 상태 · 판단 증거 · 대기 의도 · 계좌를 바꾸지 않는다.
7. 새로 수락된 의도는 이전 대기 의도를 대체하고, 두 판단 trace를 남기며, `SUPERSEDED` 산출물을 만들지 않는다.
8. 전략의 경제적 의도에는 선택자 권한이 있는 `decision_time`이나 `effective_after`가 없고, 엔진이 현재 사건의 평가
   시각을 판단 시각으로 찍는다.
9. 성공한 종료에는 대기 의도가 없다.
10. 일별 · 분별 · 불규칙 입력 밀도는 판단 사건의 집합 · 시각 · 순서와 독립이다. 선택되지 않는 체결 행만 더하면 콜백
    순서와 통제된 전체 trace가 같다.
11. 별도의 거래소 달력 · provider · 유도 경로가 없다. 체결표의 행과 관측 coverage는 판단 사건을 만들지 않는다.
12. 전략은 미래 일정을 읽지 않는다. 월말 같은 cadence는 일정 선언으로 표현한다.
13. warm-up 콜백은 전략 상태를 갱신한 `Hold`로 기록되고, 그 뒤의 결측은 실패한다.
14. 같은 얼린 일정 · 구간과 완전한 얼린 입력은 같은 콜백 · 대기 · 체결 · 계좌 trace를 만든다.

**데이터**

15. 등록의 보편적 시각 필드는 `available_at` 하나이고, 그것은 **컬럼**이다. 설정이 준 규칙을 평가하는 경로는 없다.
16. 등록에 SQL 문장은 없다(필드 값은 식이다). 준비는 전부 패키지 밖이고, 패키지에 xlsx · csv를 읽는 코드는 없다.
17. 등록 가능한 dataset의 계약이 기계가 읽을 수 있게 공개된다.
18. 경로 · 파티션 · 물리 컬럼 이름은 소비자 API에 나오지 않는다. 넓은 표를 필드 폴더로 옮겨도 소비자 선언이 같다.
    단일 parquet과 hive 파티션은 같은 선언으로 같은 결과를 낸다.
19. 등록 **뒤**에 `SourceSpec`을 직접 여는 경로가 없다. 파일 내용은 등록 때 한 번 재고, 이후엔 지문만 대조한다.
20. dataset의 identity는 선언이다. 파일이 바뀌면(행을 덧붙여도) 지문이 달라져 읽는 쪽이 거절하고, 같은 선언으로
    재등록하면 잰 반쪽만 바뀐다.
21. 미래를 반영한 값이 든 parquet의 등록은 실패하지 않는다(패키지는 판정하지 않기로 한 것을 판정하지 않는다).
22. `lookback`은 저장소 질의까지 내려간다. 미래 방향 `Lookback` 타입이 없다.
23. `RowsLookback`은 panel grain에서 pivot된 행을 세고, `InstantsLookback`은 `rows` grain에서만 허용된다. 바꿔
    쓰면 이름을 대며 거절된다.
24. 모델에서 lookback 없는 조회로 가는 경로가 없다. 모델에서 체결표로 가는 경로가 없다.
25. 기록된 표와 다른 run의 결과는 `DataRequirement`로 읽힌다. 별도 조회 경로가 없다.
26. 생산자는 계산 결과의 `available_at`을 쓸 수 없다.

**판단**

27. `portfolio`와 `signals`는 `domain` 밖의 vqapr을 import하지 않는다.
28. 가중 함수는 결측 이름을 버리고 재정규화하지 않는다. 결측 채우기 helper가 없다.
29. 모델을 새로 만들고 commit된 상태를 복원하면 다음 결과가 같다. memory나 payload 밖에 영향을 주는 속성이 숨지 않는다.
30. memory 스냅샷은 분리된 사본이고, payload를 저장한 뒤 런타임 텐서를 바꿔도 과거 payload는 변하지 않는다.
31. `Hold` 콜백도 모델 상태 스냅샷을 남기고, 실패한 콜백은 이전 상태와 대기 의도를 남긴다.
32. payload 없는 모델은 엄격한 JSON memory만으로 전과 같이 돈다.
33. 작업 checkpoint는 같은 얼린 작업 안에서만 복원되고, 추론이나 하류 입력으로 해석되지 않는다.
34. 롤링 CNN은 하위 기간마다 새로 초기화하고, 시간을 따라 이어지는 것은 OOS 점수뿐이다.
35. 상태를 쓴 DataModel의 출력은 순차 생성 표시와 소비한 모델 상태 참조를 든다.
36. 엔진에 전략 cadence를 해석하는 코드가 없고, 모델 상태 저장 · 복원 코드는 한 곳에 있다.
37. 전략 콜백 안에서 다른 run을 돌리는 경로가 없다.
38. DataModel 결과는 체결을 지나지 않는다. `DataCall`에는 계좌가 없다(경로의 부재로).
39. 전략은 다른 전략의 저장된 결과를 `DataRequirement`로 읽는다.
40. `PortfolioIntent` 생성은 `Σw + cash = 1`과 현금 범위를 검사한다. 종목별 상한은 생성에서 검사하지 않는다.
41. 같은 membership 산출물을 소비한 bucket run들은 lineage로 그것을 증명한다. bucket 합성 팩터와 부호 있는 직접 팩터가
    마찰 없는 profile에서 일치한다.

**체결과 계좌**

42. 체결 경로에 제약 평가가 없다.
43. 거래할 수 없는 종목은 제외가 아니라 현재 비중 고정으로 다룬다.
44. 체결표 조회는 `DataRequirement` · 창을 지나지 않고, `available_at` 없이 `trade_at = 체결 시각` 등호로 찾는다.
45. 선언한 체결 가격이 없으면 다른 컬럼으로 대체하지 않는다. 관측되지 않은 시각의 행을 이전 값으로 합성하지 않는다.
46. 거래 불가와 관측 부재는 0주 체결이고, `is_tradable = true`인데 가격이 없을 때만 batch 실패다.
47. 존재하는 `(trade_at, instrument)` 키의 중복은 원자적 실패이고, 요청한 종목 행의 부재는 0주 체결이다.
48. 매도가 매수보다 먼저이고, 현금 부족은 매수를 델타 큰 순(`instrument_id` 동점 처리)으로 자르며, 비례 축소하지 않는다.
49. KRX의 빠른 길과 느린 길은 같은 결과를 낸다.
50. 분수 · 로트 규칙은 거래소 규칙에 있고 `AccountMode`에 없다. `AccountMode`들의 차이는 음수 보유의 유효성뿐이다.
51. 종목에는 거래소 정보(`exchange_id`)가 없다. 비용은 종목 id가 아니라 종류에 붙는다.
52. 제약은 물리 보유에만 걸리고 look-through 노출에는 걸리지 않는다.
53. 상장은 거래소의 얼린 설정에 있고 `RunDefinition`에 없다.
54. commit 전 실패는 보유 · 현금 · 버전 · 원장을 바꾸지 않는다.
55. 계좌 이력 접근은 전략 상태 보유와 독립이다.
56. 원장은 체결을 모른다 — `domain/account.py`는 `domain/fill.py`를 import하지 않는다.
57. 평가는 매 시장 시각에 하고, 정지 종목은 원래 `observed_at`으로 이전 가격을 이어 들고, 가격이 한 번도 없던 보유는
    평가에서만 빠진다.
58. 체결 없는 시각의 평가는 `account_version`을 올리지 않는다.
59. 보고서는 intended · requested · dealt · committed · marked를 구별한다.

**Compliance와 확장점**

60. `compliance:` 없이 선언한 run이 정상으로 돈다(`UC-CONSTRAINT-001`).
61. 한도를 넘은 판단은 run을 멈추지 않고, 위반은 Compliance 발견으로 남는다. 발견은 어느 규칙인지와 그 시각의 한도와
    잰 값을 든다.
62. 전략의 상자가 필요로 하는 PIT 데이터가 없으면 **포트폴리오 결과를 만들기 전에** 실패하고, 규칙이 필요로 하는
    데이터가 없으면 **발견을 만들기 전에** 실패한다.
63. 거래할 수 없는 종목의 비중 고정은 Compliance 발견으로 보고되지 않는다.
64. 출하하는 거래소 · Compliance 구현이 쓰는 API는 공개 표면 안에 있다. preflight는 출하한 것과 프로젝트의 것을
    구별하지 않는다.
65. `vqapr new`가 내는 템플릿은 처음부터 규격 검사를 통과하고 쓴 그대로 돈다. pytest와 `vqapr register`는 같은 규격
    검사 코드를 부른다.
66. 등록 뒤 컴포넌트 소스가 바뀌면 run은 돌고, 기록이 등록된 지문과 실제로 실은 지문을 나란히 남긴다.
67. 사용자는 내부를 import하지 않고 `vqapr.public`과 `vqapr register`만으로 자기 컴포넌트를 검증한다.

**표면과 배치**

68. 소스 · 패키지 · import · CLI 이름이 모두 `vqapr`이다.
69. 저자 표면은 `vqapr.public` 하나다.
70. CLI는 `public`과 application 층과 `domain.errors`만 import한다 (경계 테스트).
71. 두 모듈이 같은 파일 이름을 가지는 것은 허용 목록 `{base.py}` 안에서만이다 (경계 테스트).
72. 층 표(`LAYERS`)의 모든 import가 엄격히 아래로 향하고 `OPEN`이 비어 있다.
73. 표준 라이브러리 모듈 이름을 가리는 모듈이 없다 (ruff `A005`).
74. `utils/` · `helpers/` · `common/` · `config/` · `workflow/` · `contrib/` · `toolkit/`이 없다.
75. 의존성에 시각화 라이브러리가 없다. 보고서에는 가격 dataset을 읽어 수익을 만드는 경로가 없다.
76. `record/`는 `run/`을 import하지 않는다.
