vqapr 0.14.2 시나리오 디버거 — 사용자가 하는 일 여섯 가지 + 배치 하나, 프레임워크 안에서 한 프레임씩

일곱 시나리오를 차례로 따라갑니다. vqapr new sample이 만든 프로젝트(10종목, 2022-01-03 ~ 2024-12-30, 735세션)에서 ① 데이터를 등록하고, ② 등록이 거절되는 두 경우(파일에 없는 컬럼 · 등록 뒤에 바뀐 파일)를 보고, ③ DataModel을 돌려 firm characteristic(5일 모멘텀)을 dataset으로 쓰고, ④ 그것을 읽는 factor 전략(상위 3 롱 · 하위 3 숏)을 돌리고, ⑤ memory로 진입가를 기억하는 stop-loss 전략을 돌리고, ⑥ ④가 저장한 alpha 비중을 읽어 enhanced index를 만들고, ⑦ ④와 ⑤를 --jobs 2로 한 배치에 돌립니다. 0.13.0 페이지와 같은 일곱 시나리오이고 계산된 숫자는 하나도 다르지 않습니다(record digest 83/83). 달라진 것은 선언에서 run까지의 길입니다: check · run · --jobs worker가 전부 문 하나(verify_run)를 지나고(기록 240–241), 그 문이 사실(agenda · 집행표 · horizon · import한 부품)을 명령당 한 번 읽고(RunFacts, 기록 238–240), run은 그 문이 load한 것을 그대로 받아 다시 import하지 않습니다(RunResources, 기록 242). 0.13.0의 check가 3년짜리 agenda를 두 번 유도하던 자리(4,271 ms · 90,168 호출)가 한 번(2,261 ms · 48,326 호출)이 된 것이 ②에 보이고, worker가 처음으로 판정을 받는 것이 ⑦에 보입니다. 프레임마다 위에는 지금 무슨 일이 일어나는지를 보통 말로 적었고, 아래 접힌 곳에 트레이스가 기록한 호출 순서를 두었습니다. 모든 #idx(그 명령 안에서 몇 번째 호출인지)와 ms는 sys.setprofile이 실제로 기록한 값이고, 스니펫은 그 시점의 소스 줄입니다 — 상상한 것은 없습니다(experiments/exp_246_the_scenario_trace_0_14_2/).

이 페이지에 나오는 낱말 — 먼저 읽어 두면 편합니다

선언 (declaration) — 당신이 쓰는 YAML. "이 parquet은 가격이다, 이 파일은 내 전략이다, 이 run은 이렇게 돌려라".
등록부 (workspace) — .vqapr/workspace.yaml. register가 쓰고, 모든 명령이 맨 처음 펼쳐 읽는다. 코드에선 Workspace.
문 (validation door) — data/validation.py. 물리 파일은 등록될 때 여기서 한 번 잰다(스키마 · key · span · 값 · 집행 가격 · digest). 이후의 모든 읽기는 파일 내용이 아니라 digest를 대조한다(require_verified). 기록 234.
문 하나 (verify_run) — flow/declaration/verify.py. 등록된 run 선언에서 FrozenRun까지 가는 유일한 길. 판정(judgments)과 얼리기(preflight)를 한 번의 읽기로 하고 RunVerdict(failures · blocked · frozen · refusal · resources)를 돌려준다. check는 그것을 그려 주고 run·worker는 require_ready()로 받는다. 기록 240–241.
RunFacts — verify_run 안에서 사실을 한 번만 읽는 그릇: agenda · 집행표 · horizon · import한 전략/거래소/규칙. 처음 물은 쪽이 읽고 나머지는 그 값을 받는다. 읽기가 실패하면 같은 예외가 물은 모두에게 간다. 기록 240.
RunResources — verify_run이 load한 인스턴스와 자른 horizon을 run에 건네는 값. FrozenRun은 record 값이라 살아 있는 객체를 못 들기 때문에 따로 간다. run은 다시 import하지 않고, 다른 run의 것이면 거절한다. 기록 242.
digest · 측정된 반쪽 — 파일 바이트의 sha256. 등록의 선언된 반쪽(컬럼 · key · grain)은 사용자의 것, 측정된 반쪽(span · digest · 집행 가격)은 문의 것. 파일이 바뀌면 같은 선언으로 다시 등록해 측정만 갈아 끼운다.
검사·판정 (check · judgment) — "이 run을 돌려도 되나"에 대한 예/아니오 하나하나. check는 모아서 답하고, run은 첫 거절에서 멈춘다. 답하지 못한 판정은 judgment.blocked로 원인 예외를 통째로 든다.
얼리기 (freeze → FrozenRun) — 등록부에 적힌 이름들을 실제 값(코드 fingerprint, parquet 경로와 digest, 결정 시각들, 초기 계좌)으로 풀어 묶은 불변 스냅샷. 이 뒤로 등록부가 바뀌어도 run은 이것만 본다.
horizon (run의 지평) — [start, end]. store가 이것을 들고, panel은 "start에서 가장 이른 lookback 하한 ~ end"만 스캔한다(_scan_bounds). 기록 235.
창 (window) · matrix() · 블록 — 한 alias의 한 필드를 시각 × 종목으로 본 것. panel은 숫자 필드마다 float64 행렬 한 벌(블록)을 들고, window.matrix()는 그 행렬의 view(복사 없음, 마지막 행이 최신, 없는 값은 NaN)다. 기록 232 · 235.
cube — --jobs 배치가 dataset마다 굽는 디렉터리: 숫자 필드마다 .npy 하나(전 종목 × 등록 span) + instants.npy + instruments.json + present.npy + cube.json(원천 digest). worker는 np.load(mmap_mode='r')로 map 하고, 배치가 끝나면 디렉터리는 지워진다. 기록 236.
전략 시계 · 시장 시계 — agenda가 만드는 결정 시각(매일 08:00 또는 09:00)과 집행표에 행이 있는 시각(매일 15:30). 결정은 앞에서, 체결·평가·판정은 뒤에서만. 트레이스의 시장 시각은 UTC로 찍힌다(06:30 = 15:30 KST).
DataModel · materialized dataset — 세션마다 종목별 행을 돌려주는 모델. run이 끝나면 그 행들이 .vqapr/materialized/<writes>/all.parquet이 되고 같은 문을 지나 dataset으로 등록된다. 다음 run은 벤더 표와 똑같이 읽는다.
writes · 배분 dataset — 전략 run도 자기 비중(vqapr.weight)을 writes가 이름한 dataset으로 낸다. 다른 run이 그것을 alpha로 읽을 수 있다(⑥).
memory — 전략의 self.memory. 엄격한 JSON. 매 decide 전에 복원되고 뒤에 정규화되어 publish된다. 첫 콜백엔 {}.
의도서 (intent) · pending — 전략이 돌려준 목표 비중에 프레임워크가 도장을 찍은 것. 체결 시각이 올 때까지 pending으로 하나만 기다린다. Hold면 pending 없음.
봉투 (envelope) — 모든 명령이 stdout에 내는 JSON 한 덩어리. 성공이든 거절이든 모양이 같다: ok · stage · failures[code · status · requirement · observed · fix].
